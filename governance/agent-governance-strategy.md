# Agent 治理策略

这页回答一个问题：当 agent 治理变重时，哪些防线应该保留为硬约束，哪些应该降成语义门、模板字段、sensor 或周期复盘。

它不替代 [[AGENTS]]、[[POLICY]]、[[WORKFLOW]]、[[response-mode-routing]]、[[instruction-adherence]] 或 [[log-writing-rules]]。这些页面继续负责执行约束、裁定、流程、响应模式、指令覆盖和日志写法；本页负责给它们提供共同的瘦身和分级策略。

## 当前诊断

当前不合理的地方不是“治理太多”，而是多处把防漏规则写成了一刀切仪式。

| 设计点 | 过重表现 | 整改口径 |
| --- | --- | --- |
| `[[log]]` | 把所有实际内容变更都绑定到新增或补写记录，容易变成提交税 | 改成 log eligibility：先判是否影响未来理解，再决定必写、合并写或免写 |
| 响应模式 | 每轮都像要完整推导 8 个模式 | 默认先做轻量模式判断；只有命中状态、验收、规则、跨工程或长期沉淀时升级 |
| 引导式设计 | “产物化”容易被理解成每轮都要生成正式文件 | 改成产物化资格判定：有可复用意图、约束、决策候选或后续动作才落文件 |
| 二阶反思 | 每轮收尾都可能膨胀成新规则 | 改成缺口分流：单次表现只记录判断，重复或 P0 影响才进 ledger / sensor |
| 检查门禁 | 完整 `check_all.py` 可能被当成任何小改的固定动作 | 工作阶段先跑专项 sensor；跨入口、提交前或规则结构变更再跑完整门禁 |
| 模板反哺 | “规则默认反哺”容易被误读成规则默认写入 | 默认进入候选判断；通过抽象、冲突和体积检查后才写入 |
| 入口页 | 为防漏把细节继续塞进根入口 | 根入口只留 P0 guard、路由和 owning page 链接；细节下沉 |
| Goal Contract | 长时任务契约可能被泛化到普通任务 | 只用于终点明确但路径需探索的长时任务 |
| 事项链路 | Gate / FP / EP / TASK 等关系容易变成连锁同步义务 | 只在当前裁决需要时同步；参考规则不上推成隐形待办 |

## 策略原则

1. **硬约束保护 P0，不保护仪式**：用户可见事实、证据、权限、验收、写入范围、提交边界和人工确认属于 P0；格式、记录、入口同步和复盘属于可分级治理。
2. **每条硬规则都要有触发条件**：不能只写“必须做”；要写什么信号触发、做到哪一层、哪些场景免做。
3. **先语义门，后机械门**：语义上不该做的事，不用 sensor 强迫做；语义上必须做的事，再用模板、脚本或最终证明防漏。
4. **入口短，能力不短**：入口缩减只删重复说明，不删能力；能力放到 owning page、技能、模板和 sensor。
5. **规则升级必须配降级出口**：新增规则、模板字段或 sensor 时，至少标记一条 prune candidate 或说明为什么暂不清理。
6. **闭环证明分层**：clean proof、scope proof、log proof、acceptance proof 和 human-confirmation proof 是不同证明，不能互相替代。

## 分级模型

| 层级 | 名称 | 适合内容 | 默认承接 |
| --- | --- | --- | --- |
| P0 | always-on guard | 权限、写入范围、原始事实保真、验收不上推、提交边界、人工确认 | [[AGENTS]]、[[POLICY]]、sensor / finalizer |
| P1 | semantic gate | 是否写 log、是否产物化、是否跑完整检查、是否进入 Goal、是否升级规则 | 本页、[[WORKFLOW]]、[[instruction-adherence]] |
| P2 | procedure | 怎么写、怎么合并、怎么拆、怎么输出 | owning page、模板、技能 |
| P3 | advice / backlog | 候选经验、单次教训、待观察问题、可删除规则 | [[harness-feedback-ledger]]、文章、概念页 |

如果一条规则只是 P2 / P3，却被写成 P0，就会拖慢 agent 并降低遵循质量；如果一条 P0 只停留在自然语言，就会产生越权、漏验或错写风险。

## 关键语义门

### Log Eligibility

每次文件变更都要判断是否需要 `[[log]]`，但不是每次都要写一条。

**必须写**：

- 改变规则、入口、目录结构、单一信息源、自动写入边界或模板体系。
- 改变项目状态、需求口径、设计决策、验收结论、风险归口或跨工程边界。
- 产生可复用知识沉淀、Harness episode、重要复盘或长期背景。

**合并写**：

- 同一主题下的补链、补入口、补同步、轻量纠偏。
- 同一治理动作里的模板、脚本、入口和说明联动。

**免写**：

- 纯格式化、错别字、表格对齐、无语义链接修复、检查脚本无内容变更。
- 临时本地状态、缓存、草稿试运行和没有进入文档结构的探索。

提交前要证明的是“已做 log eligibility 判断”，不是“机械新增一条 log”。

### Artifactization Eligibility

引导式设计、知识沉淀和复盘不等于每轮都要落正式页面。只有出现以下任一情况才默认落文件：

- 形成了可复用方法、稳定事实、设计候选、验收标准、风险或后续动作。
- 后续会依赖这次结论继续推进。
- 不沉淀会导致用户下次重复解释。

如果只是澄清、快诊断或尚未稳定的想法，可以只在最终回复里给 checkpoint，或先放轻量 discovery。

### Check Budget

检查也分层：

- 小范围文案 / 链接修正：`git diff --check` 或相关局部检查即可。
- 单一治理面改动：跑对应 `python3 scripts/check_all.py --only <check-key>`。
- 跨入口、规则、结构、模板或提交前：跑完整 `python3 scripts/check_all.py`。

### Rule Upgrade Budget

规则升级前先问四个问题：

1. 这是 P0 风险，还是 P1 / P2 流程偏差？
2. 能不能改旧规则或补触发条件，而不是新增平行规则？
3. 能不能落成模板字段、sensor 或最终证明？
4. 这次新增后，哪条旧规则可以降级、合并或进入 prune queue？

## 整改后的默认链路

1. 先按 [[response-mode-routing]] 做轻量模式判断。
2. 命中 P0 风险时，立即升级到对应重模式和证明层。
3. 命中 P1 语义门时，先做资格判断，再决定是否写文件、跑完整检查或补 `[[log]]`。
4. 需要长期生效时，优先改 owning page；根入口只补短触发和链接。
5. 规则变更同时检查 prune candidate。
6. 收尾时说明本轮触发了哪些语义门，哪些免做，以及跑了哪些检查。

## 禁止项

- 不把“防漏”直接等同于“每次都做”。
- 不把入口缩减理解成删除能力；能力必须有可追踪落点。
- 不把 `[[log]]`、Goal Contract、完整检查、二阶反思或模板反哺写成无条件仪式。
- 不让 sensor 只检查某个词是否出现，却反向逼迫文档保留低价值文字。
- 不用一次失误直接新增硬规则；除非它影响 P0，或已经重复出现并能被模板 / sensor 承接。

## 当前整改目标

- [[log-writing-rules]]：从“必写记录”改为“必做资格判断”。
- [[instruction-adherence]]：触发矩阵从固定动作改成 log / check / artifact eligibility。
- [[WORKFLOW]]：把收尾顺序改成先判语义门，再补必要同步。
- [[AGENTS]]：根入口只保留短触发，不展开细节。
- [[harness-feedback-ledger]]：新增“硬性治理过度” episode，并把规则降级 / 删除从 backlog 提升为周期动作。

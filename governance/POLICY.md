# 规则层

这页属于治理层，统一由 [[governance/README]] 收口。

这页放共享规则、优先级和记忆路由约束。

## 这页负责什么

- 定义哪些内容可以自动晋升为共享背景或项目记忆
- 定义冲突时的优先级和升级路径
- 定义共享背景、项目记忆、决策和会话的边界
- 定义哪些规则必须人工确认后才生效

## 这页不负责什么

- 不放项目阶段的具体取舍，那进 [[projects/decisions]]
- 不放项目内需求到实现的完整演进链，那进 [[projects/trace]]
- 不放时间顺序上的主题化过程记录，那进 [[log]]
- 不放逐条对话转录，那留在会话历史
- 不放单轮会话草稿，那留在会话 / 临时收口区
- 不放共享背景正文，那是 [[BRAIN]]
- 不放下游项目事实或业务决策；模板反哺只吸收抽象后的系统层信息，具体执行看 [[template-feedback-rules]]

## 读取优先级

- [[POLICY]]
- [[projects/decisions]]
- [[projects/memory/README]]
- [[projects/memory/shared]]
- [[BRAIN]]
- `workspace-memory`
- session / chat history

## 自动沉淀规则

### 规则 1：默认都先不进长期记忆

- 新信息默认先留在会话、`inbox/` 或临时草稿
- 没有满足晋升条件前，不直接写入 [[BRAIN]]、[[projects/memory/shared]] 或 [[POLICY]]

### 规则 2：满足条件才升到共享背景或项目记忆

满足下面任一条件时，才考虑从 session 晋升：

- 同一件事多轮重复出现
- 明确会影响后续多个任务
- 明确属于项目共识
- 如果不沉淀，下次会重复沟通

晋升方式：

- 跨任务但仍属于共享前提的，进入 [[BRAIN]]
- 只对当前项目长期有效的，进入 [[projects/memory/shared]]

### 规则 3：只有拍板后的内容才进规则层

以下内容只有在已经确认后，才进入这页：

- 冲突升级规则
- 自动沉淀边界
- 优先级顺序
- 例外处理规则

### 规则 4：发生冲突不直接覆盖

固定流程：

1. 标记冲突
2. 写到 [[projects/decisions]]
3. 等拍板
4. 再回写 [[BRAIN]]、[[POLICY]] 或项目页

## 自动写入边界

- agent 每轮必须先按 [[response-mode-routing]] 判断本轮响应模式。快速诊断、知识沉淀、Issue 分析 + 沉淀、验收关闭、规则升级、子工程实现 / 回传和批处理的读取深度、默认写入和收尾动作不同，不得用同一套重治理动作覆盖所有问题。
- 当用户提出新系统、新工具、新应用、粗糙产品想法，或要求更智能、更前沿、更高效但没有定义成功标准时，默认按 [[proactive-dialogue-system]] 进入引导式设计。agent 可以自动提出少量关键问题、声明假设并生成草案，但不能替用户拍板业务目标、预算、真实 owner、合规、生产事实或最终验收。
- 如果规则已经存在但没有被执行，先按 [[instruction-adherence]] 判断该补触发器、模板字段、sensor、门禁或最终证明；不得默认继续堆自然语言硬规则。
- 执行类页面必须按 [[execution-contract-semantics|执行合同语义]] 保持当前裁决单值。参考规则、条件路由、非目标、上层发布 / 准出证据和辅助日志不能下沉为当前 TASK、issue、AP 或报告目标包的隐形待办。
- 快速诊断模式默认不写项目状态、不关闭 TASK / EP / FP / Gate、不提交规则变更、不把候选结论写成验收完成；TODO 仅作轻量兼容视图。若诊断结果影响项目状态、长期事实、验收或规则，必须显式切换到对应模式。
- 为了提速而削弱用户可见症状保真、证据分层、权限边界、非默认值验证、人工确认边界或提交闭环，属于无效优化。
- 为了显得智能而无限扩大读取、长期追问、一次铺满项目结构、静默替用户拍板高风险事项，属于无效智能化。有效智能化必须同时写清场景包、假设、待确认项、产物落点和性能预算。
- Goal Contract 只用于长时任务的完成契约：写清期望最终状态、完成判定、验证面 / 证据边界、预算 / 阻塞停止条件、约束、允许边界和明确不做项；它不能替代项目状态、TASK / EP / FP / Gate / release 关闭标准、验收报告、规则层或 memory，普通一次性任务不默认套用。Goal 的默认用途是防止任务跑偏、防止证据漂移、防止无限探索；health、日志、子工程自述和中间态不能因为写入 Goal 就被上推成真正闭环。
- `Gate -> FP -> EP -> TASK` 是研发事项默认主链；risk、issue、test、验收、报告和服务台账是关系节点。agent 可以补齐矩阵和模板字段，但不能用单个 TASK、单次接口成功或单份报告自动关闭父 EP / FP / Gate。
- 未实际发生的问题只允许写成 risk 或 `issue-trigger:`；已发生的 bug、偏差、验收失败或用户可见问题才进入 Issue 案件。Issue 必须保留原始现象，不能被推测根因、日志摘要或修复说明改写。
- agent 可以自动写入：`inbox/`、临时草稿、已确认结构下的普通项目页、已确认模板的 frontmatter
- agent 可以自动写入 [[log]]，但只记录按对话整理后的主题、用户意图、关键动作、结构变化和结论，不机械转录每个提问
- agent 可以自动写入 [[projects/trace]]，前提是这轮已经形成明确的项目推进内容，而且该变化会影响当前需求主题的实现口径；写入时要和相关 [[projects/requirements]]、[[projects/design/README]]、[[projects/decisions]] 同轮联动，不把它写成第二份 [[log]]，也不记录原始来源材料清单、出处或格式转换过程
- agent 必须把有项目价值的新信息同轮沉淀到正确位置：需求变化、事实纠偏、架构判断、决策倾向、待讨论问题、实现计划、风险、环境约束和用户明确偏好，不得只留在最终回复里。
- agent 必须显性化新发现的阻塞、问题和待拍板事项：只要影响当前阶段、Gate 准入、下一步、风险归口或会议议题，就同轮更新 [[projects/status]]、[[projects/development/risks/README]]、[[projects/meetings/README]]、[[projects/development/execution/todo]] 或 [[projects/decisions]]；需要用户或 owner 决议的事项只能标为待定 / 会议议题。
- 对外 API、调度入口、服务间回调、webhook、跨工程数据合同和数据库写入接口属于稳定合同；新增或变更时必须进入正式中文文档，不能只留在 handoff、测试报告或最终回复中。
- 代码工程或外部工程 agent 对本库默认是只读上下文；直接写入本库属于受控回写，必须由任务说明明确授权写哪些页面。未授权或无写权限时，自动输出边界是代码工程内的回传包。
- 本库侧 agent 对代码工程或子工程默认也是只读和验收取证；除非用户明确授权修改该子工程，否则不得为了传递验收结论、补 handoff 或关闭争议而直接改子工程文件。
- agent 可以自动执行格式归一化：把本库内错误的 Markdown 页面引用收敛成 `[[wikilink]]`，把明显失效的空链接、占位链接和本机绝对路径引用修正掉
- agent 可以在收尾或被用户指出重复 / 同类问题时，做二阶反思并自动更新既有流程、执行约束、模板入口或 [[log]]；如果反思会新增高优先级规则、改变自动写入边界、改变优先级或覆盖旧规则，必须先按冲突流程升级。
- agent 可以在用户要求反哺模板时，按 [[template-feedback-rules]] 把下游项目中已经验证的结构、流程、规则、记忆路由、模板、写法和自动化契约抽象回模板库；抽象时不得复制项目事实、业务状态或具体技术拍板；“规则默认反哺”只表示默认进入候选，写入前必须通过抽象、冲突和单一信息源检查
- agent 可以把用户纠偏、检查失败、模式切换、重复失守或明显可脚本化缺口写入 [[harness-feedback-ledger]]；episode 记录只代表 Harness 反馈数据，不自动晋升为 [[AGENTS]]、[[POLICY]] 硬规则，也不自动关闭项目事项。
- agent 可以自动写入 `skills/` 下的项目内技能页，前提是该技能只承接可复用分析流程、判断框架、输出格式和回写守卫；技能页不得替代项目状态、需求、设计、EP / TASK 状态、轻量 TODO、测试报告或服务台账的单一信息源。
- 下游项目的技能可以反哺为模板技能，但只能吸收抽象后的触发条件、事实源分层、定位方法、分工方式、验证方案、输出格式和禁止项；项目业务链路、数据表、运行 ID、服务实例、本地路径、仓库提交规则和一次性 handoff 不进入模板技能。
- agent 不可以把“采纳某项目设计”自动解释成整库同步、整目录复制或原样搬运下游项目设计；跨项目采纳必须先列候选分类和不反哺边界，禁止先写入项目事实再事后筛选
- agent 需要先形成明确结论再写入：[[BRAIN]]、[[projects/memory/shared]]
- agent 不应直接拍板写入：高优先级规则、冲突结论、覆盖旧规则的变更
- 任何会改变后续执行方式的内容，优先先进入 [[projects/decisions]] 再回写

## 验收与人工确认规则

- 验收时必须区分本次验收对象：`handoff / artifact 包`、`代码实现`、`联调闭环` 或 `Gate 准出`。证据只对当前对象生效，不能自动上推成更高一层的关闭结论。
- 功能验收必须形成“测试方案 -> 测试用例 / 检查点 -> 测试结论”的最小闭环。大功能、跨模块功能、Gate 准出或会影响真实数据 / 调度 / 写入 / 权限的功能必须有完整测试方案和用例矩阵；小功能也要写清测试点、结论和未验证边界。
- 标准验收和发布 / Gate 验收必须先有事项页测试计划或 `AP-*` 验收计划；测试报告必须引用计划来源。没有计划来源的报告只能作为临时观察或排障记录，不能单独作为关闭、准出或发布确认依据。
- 环境是证据面，不是荣誉阶梯。环境路由先看验收对象和关闭合同，再看哪些证据无法在低风险环境获得；只有证据需求触发时才进入更高风险或更真实的环境，并写清不上推边界。
- 跨服务或多组件验收必须按 `local validation`、`service-side validation`、`end-to-end validation` 分层写证据。局部模块成功、接口返回成功或单侧状态成功，不能自动等价为用户行为闭环完成。
- 多工程联调接口验收必须先确认接口语义：请求成功、排队中、执行中、完成、失败、取消中、已取消、部分成功、重试中分别表示什么；异步接口不能把“请求已收到”包装成“后台效果已完成”。
- 测试报告必须和 EP / TASK / ISSUE / FP / Gate 建立双向关联。没有回链关系的报告只能算孤立证据，不能单独作为关闭、准出或推进阶段的依据。
- Issue 是案件档案，报告是每次验证记录。复验失败、反向回归、人工截图、DB readback、配置恢复和服务组检查都写进报告，但已发生问题的原始现象、责任边界、最新有效报告和关闭裁决必须回到 Issue。
- 服务台账是运行实例事实单一信息源。验收涉及真实服务、UI / API 配对、profile、配置文件、代码版本、数据目录、scheduler、worker 或 sidecar 时，报告必须引用或更新 [[projects/service-registry]]，不能只写命令输出。
- 验收时不能把已有文档、handoff README、历史测试报告、口头结论或状态字段当作“已经验证”的替代品；只要本轮要给出通过 / 关闭判断，就必须做独立证据检查。
- 只要验收涉及请求参数、配置参数、profile、feature flag、限流值、重试上下文、采样数量、筛选条件或其他会改变执行结果的开关，就至少验证一个非默认值或边界值，并证明它真实改变了 artifact、progress、manifest、状态投影、SQL 结果或其他执行结果。
- 测试方案、用例和回归范围会随项目演进；新增功能、修复 bug、发现漏测、验收失败、复验结论变化或合同 / 配置 / 数据边界变化时，必须判断是否升级测试计划。
- 如果发现 owner、凭据、真实环境、真实业务结果、UI 截图、阶段准出、外部系统事实或业务拍板仍需人工确认，必须同轮列成 `待人工确认项` 并同步到 TASK、父 EP、风险或会议归口。未确认前，相关 TASK / EP / FP / Gate 只能停在 `review`、`blocked` 或待定状态；TODO 只作轻量兼容视图。

## 技术选型判断规则

当一轮工作进入“需要选定某项技术、工程工具、架构组件、数据存储、测试工具、部署方式或 UI 技术栈”时，不能只写概念解释或单点结论。

合格的技术选型至少写清：背景依据、决策问题、候选方案、决策依据、利弊分析、当前状态、影响和后续动作。未拍板内容只能标为推荐倾向或待拍板候选，不得伪装成正式决策。

## 路由规则

- 响应效率治理先看 [[response-mode-routing]]：它决定本轮先轻量诊断还是进入沉淀、验收、规则升级、实现回传或批处理；其他页面按该模式决定读取范围和写入范围。
- 临时会话信息先留在会话或 `inbox/`
- 时间顺序上的历史记录进入 [[log]]；记录单位是“每次对话”，不是“每个问题”或“每天一个主题”；如果要写用户提问，只记录能代表该次对话主题的提炼意图，相关问题可合并，不抄问题清单
- 需求从原始意图到当前实现的演进链进入 [[projects/trace]]；它按需求主题维护，不按日期分组，也不替代 [[log]]。原始来源整理、文件改名、PDF 到 Markdown / PDF->md、链接清理和出处索引不进入 [[projects/trace]]
- 全新应用探索期如果同时存在多个候选方向，默认先走 `inbox/`、`raw/`、`articles/`、`concepts/` 的轻量路由；只有某个方向被明确选为当前项目，才把它写进 `projects/`、[[projects/requirements]] 和 [[projects/trace]]
- 当前项目内反复出现的 agent 分析流程、定位套路、输出格式和回写守卫进入 `skills/`；技能引用项目事实时只写读取和回写入口，不复制正式正文。
- 重复出现、且只对当前项目长期有用的信息，先进入 [[projects/memory/README]]
- 跨任务、跨会话、但仍属于共享背景的信息，进入 [[BRAIN]]
- 会改变后续执行方式的内容，进入 [[POLICY]]
- 项目冲突和最终拍板，进入 [[projects/decisions]]
- 文档库本体的框架级说明和层级边界，默认写根 [[README]]；如果需要补背景，写 [[BRAIN]]；如果需要写规则，写 [[POLICY]]
- 下游项目反哺模板时，先进入 [[template-feedback-rules]] 的判断流程；可复用的结构写入口和结构页，可复用的执行顺序写 [[WORKFLOW]]，硬约束写 [[AGENTS]]，规则边界和记忆路由写 [[POLICY]]，共享背景写 [[BRAIN]]，可复制写法和模板骨架写 `templates/`
- Harness 自演进先进入 [[harness-evolution]] 和 [[harness-feedback-ledger]]；只有重复出现、影响面大或已经能由 sensor / 模板稳定表达的 episode，才继续晋升到 [[WORKFLOW]]、[[AGENTS]]、[[POLICY]]、技能或脚本。
- 可复用的 agent 技能写 [[skills/README]] 和对应 `skills/<name>/SKILL.md`；如果技能页成为高频文件类型，再补 [[templates/skill-template]]。
- 如果反哺候选和既有规则冲突，或者会覆盖旧规则、扩大自动写入边界、改变优先级顺序，先按冲突处理流程升级，不直接写入模板默认规则
- 除非明确是当前项目的结论，否则不要把这类内容写进 `projects/`、`projects/memory/` 或 `projects/design/memory/`

## 优先级顺序

- [[POLICY]] 高于 [[projects/memory/shared]]
- [[projects/memory/shared]] 高于 [[BRAIN]]
- [[BRAIN]] 高于 `workspace-memory`
- `workspace-memory` 高于 session / chat history

## 冲突处理

- 如果新信息与现有规则冲突，先不要直接覆盖
- 先在 [[projects/decisions]] 或相关页面写清楚冲突和背景
- 如果冲突影响后续路由、优先级或自动沉淀边界，再回写这里
- 只有确认后，旧规则才可以被新规则替换

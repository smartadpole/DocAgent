# 状态与约束推演

这页是计划型问题的治理真相源。它回答一个比“下一步做什么”更上游的问题：

> 一条新信息进入系统后，它改变了哪些状态、依赖、阻塞和可执行性；在这些变化还没被推演清楚前，哪些计划节点不能直接写进去。

它不替代 [[response-mode-routing]]、[[proactive-dialogue-system]]、[[execution-contract-semantics]] 或具体项目计划页。它只解决一个问题：不要把意图、愿望或局部事实，直接写成当前可执行安排。

## 何时使用

命中以下任一信号时，先用这页，而不是直接列行动清单：

- 新信息会影响时间窗口、先后顺序或截止日期。
- 某动作依赖权限、资源、钥匙、账号、签约、审批、预算、物流、服务可用性或他人确认。
- 用户给的是目标、愿望、偏好或粗安排，而不是已验证可执行的当前计划。
- 同一个变化会牵动多个节点，例如搬家、旅行、办证、采购、部署、上线、联调、验收、签合同。
- 你发现自己正在用“用户说 A，我写 A；用户说 B，我写 B”的线性记录方式处理计划。

## 核心原则

- 先更新系统状态，再更新计划。
- 先做约束传播，再写动作安排。
- 把意图和事实分开，把愿望和承诺分开，把候选动作和当前可执行动作分开。
- 任何依赖权限、资源、时间窗或外部确认的动作，默认都要先做可执行性判断。
- 未证明的前提不能静默当作成立；未解决的阻塞不能伪装成“后续补齐”。

## 信息归类

新信息进入系统时，先归类，不直接写计划：

| 类型 | 含义 | 例子 | 默认动作 |
| --- | --- | --- | --- |
| `confirmed fact` | 已确认现实事实 | 6.15 入住已确认 | 更新状态变量 |
| `goal / intent` | 想达到的目标 | 希望首次搬运提前 | 更新目标，不直接排程 |
| `hard constraint` | 必须满足的硬条件 | 拿到钥匙前不能保洁 | 写入约束 |
| `soft preference` | 尽量满足但可牺牲 | 想周末完成搬运 | 写入偏好，不当硬约束 |
| `assumption` | 暂按此推进但未证实 | 房东大概率可提前交钥匙 | 显式标注，可纠偏 |
| `candidate action` | 可能的动作 | 预约保洁 | 检查前提后再定 |
| `blocker` | 当前阻塞项 | 签约时间未定 | 阻塞链上提 |
| `contingent dependency` | 取决于外部事件 | 物业是否允许临时进场 | 保留条件计划 |

## 最小状态模型

计划型问题默认至少检查六类状态：

| 状态类 | 典型问题 |
| --- | --- |
| 事实状态 | 现在已经确认了什么事实 |
| 权限状态 | 谁能签、谁能批、谁能交接、谁有访问权 |
| 资源状态 | 人、钱、服务、设备、容量、时间槽是否可用 |
| 时间状态 | 最早 / 最晚窗口、前后依赖、缓冲是否成立 |
| 承诺状态 | 谁已经确认，谁只是表达意向 |
| 外部不确定 | 哪些依赖外部回复、审批、天气、物流、服务健康 |

复杂场景可再加：

- 风险状态
- 信息完整度状态
- 回滚 / 替代方案状态
- 验收状态

## 约束传播的默认顺序

### 1. 识别受影响变量

不要先写动作，先回答：

- 这条新信息改了哪些状态变量
- 哪些变量只是愿望，哪些已经变成已确认事实
- 哪些旧计划节点因此失效、提前、延后或进入不确定

### 2. 做后向推演

从目标节点往前推：

- 要让这个动作成立，必须先满足什么
- 每个前提又依赖什么
- 关键缺口是事实、权限、资源、时间还是外部确认

### 3. 做前向推演

从变化节点往后推：

- 这条变化会触发哪些下游动作提前、延后、取消或改条件
- 是否引入新的资源冲突、时间冲突或责任冲突

### 4. 检查资源与互斥

- 谁要到场
- 哪些资源不能同时占用
- 哪些事情必须串行，哪些可以并行

### 5. 区分可控与不可控

- 自己可直接决定的，属于 controllable
- 依赖外部回复、审批、系统健康或天气的，属于 contingent

### 6. 输出可执行性结论

每个动作只允许落在这几类之一：

- `executable`
- `conditionally executable`
- `contingent`
- `blocked`
- `not-in-scope`

没有结论前，不把它写成正式安排。

## 默认输出格式

计划推演的最小输出至少包含：

- **新信息**：进入系统的事实、目标或变化
- **信息类型**：事实 / 意图 / 约束 / 假设 / 动作候选 / 阻塞
- **受影响状态变量**：哪些状态被改写
- **约束传播结果**：前置链、后置链、资源链、时间链如何变化
- **已确认 / 未确认 / blocked**：哪些成立，哪些只是愿望，哪些仍卡住
- **当前可执行性**：对相关动作逐个给 `executable / conditional / contingent / blocked`
- **计划更新**：只写通过可执行性检查后的动作调整

## 报告资产

这套方法不只是一张总模板，也可以拆成多张按维度复用的报告资产：

- [[templates/state-constraint-overview-template]]：首轮统一建模，总览状态、约束和计划更新。
- [[templates/state-executability-report-template]]：单个动作或子计划的可执行性裁决。
- [[templates/dependency-propagation-report-template]]：关键变化后的上下游传播分析。
- [[templates/time-resource-window-report-template]]：时间窗口、资源可用性和互斥冲突分析。
- [[templates/blocker-uncertainty-report-template]]：阻塞项、外部不确定和推进边界分析。

使用原则：

- 问题还没看清时，先用 `overview`。
- 用户真正要的是“现在能不能做”，优先用 `executability`。
- 核心是某条变化会怎样连锁扩散，优先用 `dependency propagation`。
- 核心是排时间和资源，优先用 `time-resource window`。
- 核心是卡在哪和哪些没被证明，优先用 `blocker-uncertainty`。

## 一个最小例子

输入新信息：

- 6.15 入住
- 入住前可拿钥匙

不要直接写：

- 6.12 保洁
- 6.13 首次搬运

先做推演：

1. **受影响变量**：
   - 签约状态
   - 钥匙状态
   - 保洁时间窗
   - 首次搬运时间窗
   - 旧房交割时间窗
2. **后向推演**：
   - 若首次搬运提前，保洁需先完成
   - 若保洁提前，钥匙需更早拿到
   - 若钥匙更早拿到，签约 / 交接需更早完成
3. **未知项**：
   - 提前拿钥匙是已确认承诺，还是口头可能
   - 物业是否允许提前入场
   - 保洁和搬运方对应时间槽是否可用
4. **结论**：
   - `首次搬运提前` 目前只能写成 `conditionally executable` 或 `contingent`
   - 不能直接升级成当前正式安排

## 与其他治理页的关系

- [[response-mode-routing]]：决定这轮是快速诊断、引导式设计、知识沉淀还是规则升级；本页回答计划型问题里“先判什么”。
- [[proactive-dialogue-system]]：决定如何少量提问、带假设推进；本页提供计划型问题的状态和约束检查框架。
- [[execution-contract-semantics]]：治理“当前裁决是否单值”；本页治理“这个裁决在进入执行面之前是否已被证明可执行”。
- [[instruction-adherence]]：如果系统已经有这条规则但反复失守，去那里升级模板、sensor 或最终证明。

## 常见错误

- 把新日期直接写成新安排，不做倒推。
- 把“可以”误当成“已经确认并且资源可用”。
- 只记录动作，不记录状态变化。
- 只写前置条件列表，不做约束传播。
- 把外部不确定静默当成已解决。
- 把 blocked 的动作继续留在当前执行面，等价于制造隐形待办。

## 路由约束

- 纯知识沉淀：优先回写 `articles/`、`concepts/` 和 [[log]]。
- 引导式设计：同时更新 [[templates/guided-discovery-session-template]] 对应的状态模型、传播结果和可执行性判断。
- 模板资产化：若某一类计划分析反复出现，优先从这组报告资产里挑对应模板，而不是临时再写一版自由格式说明。
- 项目型计划：根据成熟度回写 [[projects/requirements]]、[[projects/trace]]、[[projects/decisions]] 或正式执行入口。
- 收尾前，不把 `goal / intent`、`assumption` 或 `contingent` 动作伪装成已确认执行计划。

## 一句话检查链

`先判这条信息改了哪些状态 -> 再判约束如何传播 -> 再判什么已证明可执行 -> 最后才改计划`

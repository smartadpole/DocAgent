# 主动对话与引导式设计系统

这页定义 agent 什么时候应该主动和用户交流、怎么问、问到什么程度停止，以及如何把粗糙想法推进成可设计、可开发、可验收、可沉淀的系统成果。

它不是聊天风格指南，也不替代 [[response-mode-routing]]、[[WORKFLOW]]、[[POLICY]] 或项目研发链路。它只回答一个问题：当用户的目标还没有完整表达时，agent 如何通过少量、高质量、可收敛的问题帮助用户和系统共同把目标变清楚，并把对话所得和 agent 思考结果落到文件。

## 策略定位

引导式对话不是轻模式，也不是绕过知识库、trace、design、decision、log、检查和提交闭环的例外层。它是当前 wiki 的输入采集层和早期成形层：先把用户表达、上下文判断、agent 推理、候选拆解和待确认项收成可追踪材料，再交给知识库或研发管理链路继续治理。

固定策略：

1. 对话中形成的用户意图、场景、范围、约束、风险、验收、候选决策、拆解关系和 agent 判断，默认都是系统成果候选。
2. 引导式对话只决定“先落到轻量 discovery / owning page，还是进入正式需求、trace、design、decision、FP / EP / TASK”，不能决定“不落文件”。
3. 只有没有新增事实、没有新增判断、没有新增待确认项，且只是解释既有页面时，才允许不改文件；最终回复必须说明回看的 owning page。
4. 一旦用户纠偏“对话所得没有沉淀”，必须进入 [[instruction-adherence]] 和 [[harness-feedback-ledger]]，判断是否补模板、sensor 或收尾证明。

## 目标

- 把“你想做什么”转成可执行的意图、范围、约束、验收和下一步。
- 在不确定时主动交流，但不把每个小疑问都丢回给用户。
- 每一轮提问都推动产物变具体：需求、trace、设计专题、决策、执行包或验证计划。
- 每一轮都把对话所得和 agent 思考结果路由到系统内的 owning page。
- 让人工确认、agent 可假设项、可自动推进项和 blocked 项分开。
- 保持高效：先问少量关键问题，边假设边产出草案，再让用户纠偏。
- 逐步达到无感交流：用户不用先声明场景、角色或流程，agent 先根据上下文自动判定场景包和下一步。

## 双层架构

这套能力分成两层：

1. **通用主动对话内核**：适用于所有复杂场景，负责上下文自动判定、少量提问、假设推进、人工确认、产物收敛和收尾证明。
2. **场景化问题包**：根据当前上下文自动选择知识库、软件研发、运行排障、研究决策、个人 / 生活系统或规则治理等问题包。

原则：用户不需要先说“我现在是哪个场景”。agent 先从当前目录、已有文档层级、用户措辞、预期产物、风险类型和历史上下文推断；只有推断会影响关键方向时，才问用户确认。

## 场景包

| 场景包 | 典型触发 | 主要关心 | agent 应产出 |
| --- | --- | --- | --- |
| 知识库 / 材料吸收 | 整理材料、沉淀知识、补索引、吸收外部文档 | 信息层级、单一信息源、原始材料、影响面、链接和后续驱动 | raw / inbox 落位、article / concept、索引、trace / log / status 影响图 |
| 软件研发 | 新系统、新工具、新功能、架构、开发准备 | 用户、场景、范围、模块、接口、数据、测试、发布和回归 | requirements、trace、design topics、decisions、FP / EP / TASK 候选、验收标准 |
| 运行排障 / 验收 | 故障、复验、关闭、服务不可用、数据不一致 | 原始现象、证据层级、环境、服务组、DB / artifact / UI、关闭标准 | checkpoint、issue / report、风险、待人工确认、复验动作 |
| 研究 / 决策 | 技术选型、方案比较、是否采用某工具 | 决策问题、候选、评价维度、证据、风险和推荐倾向 | 候选矩阵、决策草案、待拍板事项 |
| 个人 / 生活系统 | 搬家、日程、物品、习惯、家庭流程、个人系统 | 当前动作、资源约束、可复用流程、风险和提醒 | 行动清单、分类规则、可复用系统、提醒或后续跟进 |
| 规则 / 模板 / Harness 治理 | 用户纠偏、规则升级、模板复用、流程过重 | source of truth、触发器、sensor、模板字段、人工语义边界 | 规则页、模板、sensor、ledger episode、log |

## 非目标

- 不把主动提问变成打扰式追问。
- 不用长问卷代替 agent 的判断、阅读、归纳和草拟能力。
- 不替用户拍板业务目标、真实 owner、预算、法务、生产事实、外部系统权限或最终验收。
- 不把探索阶段的候选想法直接升级成 [[POLICY]]、项目状态、EP / TASK `done` 或 Gate 准出。
- 不用同一套通用问题覆盖所有场景；判定进入某个场景包后，必须切到对应问题矩阵。
- 不把“无感交流”理解成静默替用户决定高风险事项；目标是少打扰，不是零确认。

## 触发信号

命中以下任一信号时，进入主动对话 / 引导式设计判断：

- 用户在新 clone、空白项目、模板工程或身份未初始化工程里只说“你好 / hi / 开始吧”等低信息问候。
- 用户说“设计一个系统”“做一个新工具”“帮我把这个想完整”“你来引导我”“还不知道怎么开始”。
- 输入只有目标愿景、痛点、灵感、截图、竞品或零散材料，但缺问题、用户、范围或验收。
- 用户要求“完善、智能、高效、前沿”等质量目标，但没有定义成功标准。
- 设计、研发或验收推进时，发现缺少不可替代的人工确认项。
- agent 面临多个合理方向，继续自作主张会改变业务目标、成本、权限或长期组织方式。

## P0 首次接触冷启动

低信息问候的首次接触 onboarding 是 P0 冷启动规则：先建立系统角色、用户目标、协作方式和第一步成果，再给常规引导方向和推荐第一步。它是首次接触 + 常规引导融合入口。

## 首次接触 onboarding

当用户只说“你好 / hi / 开始吧”时，agent 不应只是被动寒暄，也不应立刻启动 Goal、全量调研、写 log、检查状态或铺完整项目结构。默认进入 **首次接触 + 常规引导融合入口**：先帮助用户认识当前 agent / 工程、建立协作入口，再直接给出常规推进方向。

首次接触 onboarding 和使用过程引导是两个层面：

| 层面 | 用户状态 | agent 目标 | 不应出现 |
| --- | --- | --- | --- |
| 首次接触 + 常规引导融合入口 | 用户只是打招呼、第一次接触、还没决定要做什么 | 说明我是谁、能陪你建立什么，同时给出常规推进方向和推荐第一步 | 分支、dirty、本地路径、TASK / EP / Gate / Issue、diff、检查结果、提交状态、Persistence Decision |
| 使用过程项目引导 | 用户已经选择推进当前工程、状态检查、收尾、实现或验收 | 按响应模式进入项目运行层，读取事实源并给执行建议 | 把运行层动作伪装成普通寒暄 |

首次接触 onboarding 的默认动作：

1. 先用已加载上下文、当前会话已知路径或启动入口已有信息判断工程身份；不得为了问候去读文件、搜索仓库、跑命令或启动调研。若身份不确定，直接把“先定位工程身份”列为可选推进方向。
2. 用一句话正向说明当前 agent 能陪用户建立什么，例如“我可以帮你认识这套工程、选定主体定位、把想法收成一个可推进的项目入口”。
3. 给出 2 到 4 个常规引导方向，而不是开放问卷：例如 `梳理当前项目或某个主题的状态`、`写入一条新想法、规则、复盘或项目事实`、`推进一个具体实现 / 验收 / 收尾任务`、`先讨论一个还没完全成形的新系统或新工具想法`。
4. 如果当前上下文明显是在建设 wiki / agent 体系，agent 可以主动把体系分块呈现给用户校准：identity / owner、workflow、memory、harness / Goal、skills / research、evaluation / closeout、runtime / ops、clone initialization。
5. 只有用户选择了方向，或问候中同时带有明确任务，才升级到对应响应模式；否则本轮可以不写文件，并在最终回复说明没有新增可沉淀信息。

首次接触 onboarding 的输出应短、可继续、带引导感。它的目标是降低进入门槛，同时让用户知道可以立刻怎样开始。对新用户来说，它要自然覆盖四项设定：`system_role`（系统角色）、`user_goal`（用户目标）、`collaboration_mode`（协作方式）、`first_outcome`（第一步成果），并接上常规引导。

### 首次接触最低回复形态

低信息问候可以不产生日志、trace 或提交，但不能退化成纯寒暄或泛泛分叉。最低回复必须在快速路径中完成：**零工具、零读盘、零命令、零调研**。除非用户在问候里同时带了明确任务，否则不得发出 “Working...” 状态，不得先读取 README / BRAIN / projects，不得运行 `rg`、`git`、`date` 或任何检查命令。

最低回复必须包含：

1. **首次接触定位**：一句话说明当前是模板母体、待初始化 clone、既有工程助手或普通对话；身份不确定时说“我可以先帮你定位这个工程”。
2. **协作承诺**：一句话说明 agent 可以陪用户建立什么，例如理解工程、确定主体职责、把想法收成项目入口或带看 agent 体系。
3. **常规引导方向**：列出 2 到 4 个适合从当前工程开始的方向，例如梳理状态、写入新事实、推进实现 / 验收 / 收尾、讨论新系统想法。
4. **推荐第一步**：如果上下文置信度高，推荐一个 onboarding 分块；若置信度低，只问一个会改变方向的问题。

最低回复里的四项设定必须可被用户直接理解，但可以自然融合在首段，不强制四个独立标签：

- **系统角色**：这个 agent / 工程现在以什么身份陪用户工作。
- **用户目标**：用户可以先把目标定成知识库、主控模板、子工程模板、运维 agent、runtime service 或其他待识别方向。
- **协作方式**：默认用引导式对话把目标、约束、第一步产物和后续节奏收敛出来。
- **第一步成果**：本轮最小可交付应是一个定位、一个目标草案、一个项目入口或一个可继续的 agent 体系分块。

参考回复骨架：

> 你好，我在。
> 这里我会先把自己定位成这个 wiki / 软件工程知识库的协作维护者：帮你把目标厘清、按现有结构落位、把该沉淀的内容写到正确位置，并在需要时完成检查和提交。
>
> 可以从这几个方向开始：
>
> 1. 梳理当前项目或某个主题的状态
> 2. 写入一条新想法、规则、复盘或项目事实
> 3. 推进一个具体实现 / 验收 / 收尾任务
> 4. 先讨论一个还没完全成形的新系统或新工具想法
>
> 推荐第一步：你直接告诉我“这轮想解决什么”，哪怕只是一句话也可以；我会先判断它该走快速诊断、设计引导、沉淀、验收还是实现路径。

禁止把首次问候只回答成“你想继续处理这个 wiki，还是先聊点别的？”这类二选一闲聊分叉。若当前工程是 wiki 模板母体，默认推荐先展开 `clone initialization` 或 `identity-and-owner`；若用户最近正在校准 agent 体系，默认推荐先展开最相关的 agent 体系分块。

首次接触可以给出常规引导方向，但禁止主动输出这些运行事实或执行证明：当前分支、dirty / 未提交文件、本地绝对路径、`projects/README`、TASK、EP、Gate、Issue、diff、检查结果、提交状态、同步状态、`Persistence Decision`。这些内容只在用户明确选择“检查当前状态 / 推进项目运行层 / 收尾 / 实现 / 验收”后进入使用过程项目引导。

首次问候的性能预算是即时回复，目标是 3 秒内给出第一条可见回答。若当前身份无法从已加载上下文判断，宁可说“我可以先帮你定位这个工程身份”，也不能为了更精确的身份判断牺牲首次响应。

### wiki / agent 体系分块呈现

当用户在 wiki 模板母体中问候、追问“你能做什么 / 怎么开始 / 这个体系如何建设”，或上下文显示用户正在优化 agent 体系时，agent 可以选择用对话方式分块呈现当前体系，而不是一次性倾倒全部文档。

推荐分块：

| 分块 | 主要回答 |
| --- | --- |
| `identity-and-owner` | 当前工程是谁，主体职责是什么，clone 后要变成哪个 owner。 |
| `workflow-and-routing` | 本轮应该快速诊断、引导式设计、沉淀、验收、实现还是收尾。 |
| `memory-and-persistence` | 哪些内容要进 memory、trace、log、topic 或项目主页。 |
| `harness-and-goal` | 什么时候需要 Goal、Loop、Run Capsule、Worker / Evaluator。 |
| `skills-and-research` | 需要调用哪些技能，何时启动调研，证据等级是什么。 |
| `evaluation-and-closeout` | 证据、sensor、验收、finalizer 和人工确认如何证明完成。 |
| `runtime-and-ops` | 服务、配置、readback、性能、外部写入和回滚如何治理。 |

呈现策略：先给 1 到 2 个最相关分块，再邀请用户选择继续展开；如果用户已经表现出明确关注点，就直接展开该分块并给下一步建议。分块呈现只服务于理解和共同设计，不能替代正式 owner 页、profile、TASK、验收或提交闭环。

## 决策模型

每个不确定点先分到五类之一：

| 类型 | 处理方式 | 例子 |
| --- | --- | --- |
| 可直接判断 | agent 读取现有文档、代码或证据后自行处理 | 文件落位、已有入口、既有技术栈 |
| 可先假设 | 先写成明确假设并继续推进，后续让用户纠偏 | MVP 先做单用户版、先用本地部署 |
| 必须现在问 | 不问就会选错方向、越权或制造返工 | 目标用户、付费方、生产写入权限 |
| 可归为待确认 | 不阻塞当前草案，但阻塞状态关闭或发布 | 真实 owner、业务名单、法务口径 |
| 当前 blocked | 缺凭据、环境、材料或业务拍板，无法继续取证 | 无法访问生产、无法确认外部接口 |

原则：能通过阅读、推理和低风险假设推进的，不先问；会改变目标、权限、预算、生产事实或关闭结论的，必须问或标成人工确认。

## 上下文自动判定

每次进入主动对话前，agent 先做一次场景判定，不要求用户手动选择。

判定信号：

- **工作区 / 路径**：当前在主控文档库、子工程、服务运行仓库、知识库、领域系统或外部参考源。
- **用户动词**：设计、整理、沉淀、验收、排障、比较、计划、提醒、部署、修复。
- **预期产物**：文档、索引、需求、架构、任务、报告、决策、行动清单、自动化提醒。
- **已有入口**：是否已有 requirements、trace、design、issue、report、service-registry、articles、concepts、log。
- **风险类型**：是否涉及生产、写库、真实 owner、法务、隐私、资金、时间承诺或不可逆动作。
- **上下文连续性**：用户是否在延续上一轮主题、纠偏上一版设计、或把同一个问题从解释推进到落库。

判定后给出三个等级：

| 置信度 | 行为 | 用户感受 |
| --- | --- | --- |
| 高 | 直接选择场景包，声明一句轻量假设后推进 | 基本无感，不需要先回答模式问题 |
| 中 | 选择推荐场景包，带 1 个关键分叉问题或允许用户纠偏 | 少量确认，避免走错大方向 |
| 低 | 给出必要的候选场景和影响，让用户选 | 明确分叉，不假装理解 |

无感交流的默认策略：高置信自动推进，中置信带假设推进，低置信再问；任何涉及高风险人工确认的事项，即使场景置信度高，也必须显性列出。

## 提问协议

主动提问必须满足这组约束：

1. 问题数量不设固定上限；只列本轮真正决定结构、权限、成本、验收或长期组织方式的问题。
2. 问题前先给 agent 的当前理解和推荐假设，让用户只需要纠偏。
3. 能通过阅读、推理或低风险假设推进的，不先打断用户；必须人工确认的事项要显性列出。
4. 优先给选项和影响，不把开放问卷整包丢给用户。
5. 一次只问会决定下一步产物形态的问题：目标、用户、核心场景、范围、约束、验收、风险。
6. 如果关键问题较多，先按主题分组并标出优先级，或分轮处理；不能为了凑少量问题遗漏重要风险，也不能把低价值细节混进当前轮。
7. 每轮问题之后必须产出或更新一个可检查中间物，而不是只继续问。
8. 如果用户已经给了足够线索，直接生成草案，并把不确定项列成 `假设 / 待确认 / blocked`。

## 引导阶段

### 1. 意图定锚

- 这个系统一句话要解决什么问题？
- 谁是主要用户，谁是验收方？
- 现在不用这个系统时，人怎么解决？
- 第一版成功的最小可观察结果是什么？

产物：一句话产品意图、目标用户、当前替代行为、MVP 成功标准。

### 2. 场景收敛

- 最关键的核心使用场景是什么？
- 每个场景的触发、输入、动作、输出和失败后果是什么？
- 哪些场景第一版不做？

产物：核心场景、非目标、边界条件。

### 3. 约束扫描

- 数据从哪里来，结果写到哪里？
- 涉及哪些权限、隐私、生产环境、外部系统或人工操作？
- 有哪些时间、预算、部署、性能、合规或维护约束？

产物：约束清单、人工确认项、风险初稿。

### 4. 方案骨架

- 系统应分成哪些模块？
- 每个模块的输入、输出、责任和上下游是什么？
- 哪些设计专题还不能拍板？

产物：模块边界、接口 / 数据初稿、设计专题、候选决策。

### 5. 验收和执行准备

- 什么证据证明系统可用？
- 哪些测试必须本地做，哪些必须服务侧或端到端做？
- 哪些功能点可以拆，哪些仍需设计补齐？

产物：验收标准、测试层级、功能点候选、下一步执行包。

## 通用问题库

通用第一轮问题优先从这里选，不要一次全问。

| 阶段 | 高价值问题 |
| --- | --- |
| 意图 | 这个系统最想消除哪类反复成本？如果只做到一件事，是什么？ |
| 用户 | 谁每天使用，谁承担维护，谁有权说通过？ |
| 场景 | 第一个真实场景从什么触发，到什么结果结束？ |
| 范围 | 哪些诱人的能力第一版明确不做？ |
| 数据 | 输入数据来自哪里，输出结果要被谁消费？ |
| 权限 | 哪些动作会写库、发消息、改配置、触发生产副作用？ |
| 智能 | 哪些判断可以由模型辅助，哪些必须可解释、可回放或人工确认？ |
| 效率 | 哪个环节最贵：人工时间、等待时间、算力、沟通成本还是返工？ |
| 验收 | 用户看到什么、系统留下什么证据，才算这轮真的完成？ |
| 风险 | 如果系统判断错，最坏后果是什么，如何回滚或人工接管？ |

## 知识库问题包

当场景判定为知识库 / 材料吸收时，优先问这些问题：

| 环节 | 高价值问题 | 产物 |
| --- | --- | --- |
| 材料归类 | 这是原始材料、摘要、概念、项目事实、规则，还是证据？ | raw / inbox / articles / concepts / projects 落位 |
| 单一信息源 | 这类内容已有主页面吗，还是需要新建入口？ | 主页面或索引链接 |
| 影响面 | 它会驱动哪些已有需求、设计、状态、风险、会议或规则变化？ | impact map |
| 证据保真 | 原始材料是否需要保留路径、截图、日志或引用边界？ | evidence block |
| 后续动作 | 它只是归档，还是会形成待办、决策、提醒或项目更新？ | log / trace / task / decision |

## 软件研发问题包：角色 × 环节矩阵

当引导式设计从“探索”推进到“正式设计 / 开发准备”时，不能继续只用通用问题库。agent 必须先判断本轮主要面向哪个工种和研发环节，再选问题。

| 研发环节 | 面向角色 | 必问焦点 | 不应在此环节拍板 |
| --- | --- | --- | --- |
| 产品探索 | 产品负责人 / 业务 owner | 目标用户、核心场景、MVP、非目标、成功标准 | 技术栈、表结构、具体任务拆分 |
| 需求分析 | 产品负责人 / 架构师 | 业务规则、输入输出、异常路径、人工确认项、验收口径 | 未经确认的 owner、预算、合规结论 |
| 架构设计 | 架构师 / 技术负责人 | 模块边界、接口语义、数据流、权限边界、运行质量和回滚 | 具体代码实现细节和工期承诺 |
| 前端设计 | 前端工程师 / 体验负责人 | 页面入口、用户动作、状态展示、错误反馈、可访问性、人工操作闭环 | 后端内部存储结构 |
| 后端设计 | 后端工程师 / 架构师 | API 合同、状态机、幂等、权限校验、任务队列、失败补偿 | UI 文案和视觉细节 |
| 数据 / AI 设计 | 数据工程师 / AI 工程师 | 数据来源、样本、标注、特征 / prompt、评估指标、可回放和人工复核 | 产品是否上线和业务最终验收 |
| 测试设计 | 测试 / 验收负责人 | 测试对象、测试环境、固定样本、主路径、边界路径、回归范围 | 未经实现方确认的技术方案 |
| 部署运维 | 运维 / SRE / 技术负责人 | 环境分层、配置、密钥、监控、告警、回滚、容量和发布窗口 | 业务范围扩张和需求变更 |

## 其他场景问题包

非知识库、非软件研发时，先选最接近的问题包，不要硬套研发术语。

| 场景 | 优先问题 | 产物 |
| --- | --- | --- |
| 运行排障 / 验收 | 原始现象是什么，在哪个入口可见，证据来自哪一层，关闭需要什么证据？ | checkpoint、issue / report、复验动作 |
| 研究 / 决策 | 要决策的问题是什么，候选是什么，比较维度和不可接受风险是什么？ | 候选矩阵、推荐倾向、待拍板项 |
| 个人 / 生活系统 | 当前要解决的动作是什么，哪些是一次性动作，哪些值得变成可复用流程？ | 当前行动清单、长期规则、提醒 |
| 规则 / 模板 / Harness 治理 | 是补充、澄清、迁移、瘦身、sensor 还是模板字段？ | 规则改动、模板、sensor、ledger |

## 性能预算

更智能不等于每轮更重。主动对话必须同时守住四个预算：

- **读取预算**：先读入口和 1 到 3 个最相关事实源；只有写入、验收、规则升级或冲突时扩大读取。
- **问题预算**：单轮只问决定结构或风险的问题；可由 agent 判断的小问题进入假设，不进入问卷。
- **检查预算**：工作阶段先跑专项 sensor；跨入口同步或提交前再跑完整 `scripts/check_all.py`。
- **产物大小预算**：早期探索先写轻量 discovery 或 owning page 摘要；不要为未定方向铺完整项目结构。

如果一轮对话变慢，先判断慢点是必要成本、可优化成本还是应避免成本；可优化成本优先沉淀成模板、技能或 sensor，而不是继续堆自然语言规则。

## 产物路由

- 多方向灵感、竞品、截图、访谈、零散材料：先进入 `inbox/`、`raw/`、`articles/` 或 `concepts/`。
- 知识库材料吸收：先判 `raw / inbox / articles / concepts / indexes / projects` 层级，再判断是否驱动 trace、status、risk、decision 或 log。
- 一个方向已经选定但还在探索：写轻量需求、[[projects/trace|trace]] 摘要、[[projects/design/topics/README|topics]] 和待确认问题。
- 需求、范围和验收已经稳定：进入 [[projects/requirements|requirements]]、[[projects/design/README|design]]、[[projects/decisions|decisions]] 和研发拆解。
- 进入开发准备时：必须把问题映射到产品、架构、前端、后端、数据 / AI、测试、部署运维中的一个或多个角色，并把每类问题的产物落到对应设计页、专题、验收方案或执行入口。
- 开始拆实现前：按 [[WORKFLOW#0.0.1 研发文档主链路|WORKFLOW#0.0.1 研发文档主链路]] 和 [[WORKFLOW#1.9 软件研发模式|WORKFLOW#1.9 软件研发模式]] 推进。
- 长时探索且终点明确：启用 [[templates/goal-contract-template|goal-contract-template]]，固定期望最终状态、验证面和停止条件。

### 每轮产物化落地判定

引导式设计和软件研发需求拆解不能只停在聊天问答。每轮结束前必须做一次产物化判定，并把对话所得、agent 思考结果和落地判定写入本轮 owning page、轻量 discovery note、需求 / trace / design topic、决策、验收入口或下一步执行入口之一。

默认规则：

1. 只要本轮新增了用户意图、场景、范围、非目标、约束、风险、验收、候选决策、拆解关系或待确认项，就必须同轮落文件。
2. 如果还不适合进入正式 `requirements / trace / design / FP / EP / TASK`，先用 [[templates/guided-discovery-session-template]] 在合适的主页面或轻量会话记录中承接，不把早期信息只留在聊天。
3. 如果本轮确实没有任何新信息、只是在解释已有页面或等待用户回答，最终回复必须写明“本轮无新增可沉淀信息”，并给出已回看的 owning page。
4. 一旦产生实际文件变更，回到 [[instruction-adherence]] 的提交闭环：跑检查、区分脏改、提交或说明例外，并在最终回复给 commit hash。

## 完成标准

引导式设计不是问完问题就完成。至少要能回答：

- 当前处于探索、轻量项目、正式设计还是开发准备阶段。
- 当前场景包、判定依据和置信度是否清楚。
- 产品意图、目标用户、核心场景、MVP 范围和非目标是否清楚。
- 面向的研发角色和研发环节是否清楚，是否已经按角色拆分问题。
- 关键约束、人工确认项、风险和 blocked 项是否显性化。
- 性能预算、读取预算、检查预算和产物大小预算是否清楚。
- 设计专题和决策是否有落点。
- 验收标准、测试层级和下一步执行动作是否能被追踪。
- 本轮信息已经落到哪个文件；如果没有落文件，例外原因是否写清。
- 若产生文件变更，提交闭环是否给出 commit hash 或明确例外。

如果以上任一项缺失，结论最多写成 `discovery / draft / partial / blocked`，不能写成设计完成、开发就绪或可以验收。

## 高效原则

- 先草拟，再纠偏；不要把用户当需求录入员。
- 先自动判定场景包，再选择问题矩阵；不要让用户先替 agent 做路由。
- 先问决定结构的问题，再问细节。
- 先缩小不确定性最高、返工成本最大的部分。
- 每轮交流都要减少一种不确定性或新增一个可检查产物。
- 同类问题沉淀成模板或技能；重复靠用户提醒的问题进入 [[harness-evolution]]。

## 无感交流等级

| 等级 | 行为 | 使用条件 |
| --- | --- | --- |
| L0 手动问答 | 用户说明全部背景，agent 被动回答 | 场景低置信、风险高、信息极少 |
| L1 引导确认 | agent 给理解、本轮关键问题或首次问候入口的可选推进方向 | 方向未定、关键分叉未定，或用户只给出低信息问候 |
| L2 带假设推进 | agent 自动选场景包，列假设并推进草案 | 场景中高置信，风险可控 |
| L3 主动产物化 | agent 直接更新合适页面 / 模板 / 计划，收尾列未确认项 | 已有入口和写入边界清楚 |
| L4 近无感协作 | agent 根据上下文自动维护链路、检查影响面、只在高风险处打断 | 规则、模板、sensor 和项目入口都已成熟 |

当前目标是稳定达到 L2-L3：大多数普通场景不需要用户先选流程；高风险或多方向分叉仍保留少量显性确认。

## 收尾证明

涉及主动对话 / 引导式设计的最终回复至少说明：

- 本轮处于哪个阶段。
- 自动判定的场景包、置信度和关键依据。
- agent 做了哪些假设，哪些已经确认，哪些仍待人工确认。
- 已产出或更新了哪些页面 / 模板 / 任务入口。
- 性能预算是否触发扩大读取、完整检查或新建结构。
- 下一轮最值得问或做的一个动作是什么。

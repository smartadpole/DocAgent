Goal 如何串起工程事项闭环

当一个工程目标会拆成执行包、任务和已发生问题时，Goal 的价值是维持同一条完成标准：修复不是终点，证据吸收和上推边界才是闭环。

适合展示，但受众更专业

EP → TASK → ISSUE 是 Goal 的工程闭环案例

这条链路适合面向 Tech Lead、研发经理和项目负责人。它说明 Codex Goal 不只是“继续修 bug”，而是持续推动一个交付目标从执行包到任务、从问题到报告，再回到父项裁决。

EP

定义一组工作要形成的模块级闭环：输出物、协同方、包内 TASK、关闭证据和不能上推的边界。

TASK

把一个功能切片写成状态化交付合同：Done Contract、验证要求、上下游和父 EP 影响。

ISSUE

当验收失败或 bug 已发生时，保留原始现象、根因边界、关闭标准、回归守卫和最新有效报告。

REPORT

记录每轮验证的对象、环境、样本、证据和结论；报告改变裁决时，再回写 ISSUE、TASK 和 EP。

普通请求容易停在局部

  • “修一下这个 issue”可能只修代码，不回写 TASK。
  • “TASK done”可能只看本地测试，不判断父 EP。
  • “报告通过”可能被误上推成 Gate 或 FP 已闭合。

Goal 应维持完成链路

  • 先固定 EP 的最终状态和关闭证据。
  • 让 TASK 每轮按 Done Contract 验证。
  • ISSUE 只在已发生问题上收口，报告只证明本轮证据。

可复制 Goal 公式

/goal 推进 <EP 名称> 下的 <TASK 名称>，直到 Done Contract 满足，并且相关 ISSUE 的原始现象、修复证据、回归守卫和最新有效报告都已回写。每轮验证 <local / service-side / end-to-end / artifact>，只把证据上推到它能证明的层级；如果证据不足、父 EP 是否关闭需要人工裁决，或验证改变了关闭标准，暂停并报告缺口。

关键边界：闭环不等于自动上推

当前证据 最多证明 不能直接证明
TASK 本地测试通过 该 TASK 的局部实现接近 done 父 EP、FP 或 Gate 已准出
ISSUE 修复并有回归证据 该问题可按最新报告关闭或进入复核 同类风险已全部消失
报告给出本轮通过结论 本轮验收对象、环境和样本成立 上线、全量执行或未来扩展目标自动完成
使用边界

本页适合展示 Goal 在复杂工程交付中的协作价值；它不替代具体项目的 EP、TASK、ISSUE、测试报告或人工关闭裁决。

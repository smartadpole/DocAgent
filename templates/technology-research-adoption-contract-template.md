# Technology Research Adoption Contract Template

本模板用于把 research-capability 的调研结论转成采用、试验、观察或暂缓的行动合同。它防止“资料充分”被误读成“可以采用”。

## 1. 采用前置条件

| 条件 | 当前证据 | 状态 | 不满足时降级 |
| --- | --- | --- | --- |
| 当前版本和 API 已查证 |  | confirmed / likely / blocked | Assess |
| license / 使用条款明确 |  |  | Hold / Blocked |
| 安全和供应链风险检查 |  |  | Trial / Hold |
| 隐私和合规边界明确 |  |  | Hold |
| 成本、限额和退出成本明确 |  |  | Trial / Assess |
| 本地或目标环境 PoC 通过 |  |  | Trial |
| owner 和维护责任明确 |  |  | Assess |
| 替代方案已比较 |  |  | Trial / Assess |

## 2. Adopt 合同

只有同时满足以下条件，才允许建议 Adopt：

- 至少一个当前 L1 来源支撑核心能力。
- license、数据、隐私、安全、供应链没有 blocker。
- 已完成与目标约束相关的 PoC 或已有等价运行证据。
- 成本和维护责任可接受。
- 有回滚、替代或退出路径。
- 项目 owner 或决策入口明确。

允许说法：

- “建议进入设计 / 实施准备。”
- “可以作为候选方案进入项目决策。”

禁止说法：

- “已经生产可用。”
- “已经通过验收。”
- “风险不存在。”

## 3. Trial 合同

Trial 表示值得试，不表示可正式采用：

- 写清 PoC 目标。
- 写清样本和指标。
- 写清成功标准和失败退出。
- 写清成本预算。
- 写清运行记录位置。
- 写清不得上推到生产的边界。

## 4. Assess 合同

Assess 表示继续观察或补证据：

- 哪个关键事实缺失。
- 什么时候刷新。
- 需要关注哪些 release、政策、benchmark、CVE、价格或生态信号。
- 是否值得安排后续调研。

## 5. Hold / Blocked 合同

Hold 必须写原因，不写情绪判断：

- blocker 是安全、license、成本、维护、成熟度、合规还是业务不匹配。
- 是否有解锁条件。
- 是否需要保留为长期观察。

Blocked 必须写缺什么：

- 权限。
- 数据。
- 一手来源。
- 样本。
- owner。
- 当前查证能力。

## 6. 沉淀与回链

| 结论类型 | 主落位 | 必须回链 |
| --- | --- | --- |
| 技术概念 | concepts | articles / projects |
| 单篇来源 | articles | raw / concepts |
| 项目选型 | projects/design 或 decisions | requirements / trace |
| PoC 结果 | projects/development/reports | TASK / issue / decision |
| 通用方法 | skills / templates / governance | skills/README / templates/README |

## 8. 分支采用口径

### 技术专题采用

技术专题不能只回答“它是什么”，还要回答“在当前约束下值不值得继续”。采用前确认：

- 概念边界是否清楚，避免把相邻技术混在一起。
- 核心机制是否有 L1 来源。
- 生态成熟度是否来自多个信号，而不是单个爆款文章。
- 替代路线是否比较。
- 当前系统约束是否映射到该技术的优劣。
- 如果没有 PoC，只能建议 Trial 或 Assess。

### 开源工程采用

开源工程采用必须多看运行和维护，不只看 Star：

- license 是否适配目标使用。
- release 是否近期活跃。
- issue / PR 是否有维护响应。
- 安全公告、依赖和构建链是否可接受。
- 最小 demo 是否可运行。
- 关键 API 是否稳定。
- 是否存在商业服务、托管依赖或外部账号要求。
- 如果只读 README，没有代码或运行验证，不能建议 Adopt。

### 行业 / AI 赛道采用

行业 / AI 调研更容易被宣传污染。采用口径必须保守：

- 公司和产品信号是否来自一手资料或可靠报告。
- 模型能力是否有公开 benchmark、论文或可复现实验。
- 数据、隐私、监管和内容安全是否进入风险门。
- 商业模式是否能解释谁付费、为什么现在付费。
- 开源生态和平台能力是否能支撑落地。
- 如果只有趋势判断，最多给 Assess。

### 产品 / 公司采用

产品采用必须检查退出成本：

- 定价是否当前。
- SLA、数据保留、日志、训练使用和隐私条款是否清楚。
- API 限额、地域、账号、企业权限是否适配。
- 是否有替代产品。
- 是否有迁移和退出路径。
- 如果条款不可见或无法确认，写 Blocked。

### PoC 采用

PoC 的成功只证明限定条件下可行：

- 样本是否代表真实场景。
- 指标是否和决策目标一致。
- 失败样本是否记录。
- 成本和运行时间是否记录。
- 是否能重复运行。
- 是否写清不能上推到生产。
- 如果没有失败边界，PoC 结论不完整。

## 9. 研究产物质量自检

- 结论是否先于证据出现：若是，重排为证据驱动。
- 是否有“我认为”“可能不错”但没有证据等级：改写。
- 是否有“最新”“当前”“主流”但没有查证日期：补日期或降级。
- 是否有行动建议但没有风险门：补风险门。
- 是否有项目建议但没有 owner 或入口：补项目落位。
- 是否有长期价值但没有 knowledge-linking：补入口和回链。

## 10. 当前事实刷新表

| 事实类型 | 刷新触发 | 推荐来源 | 过期风险 |
| --- | --- | --- | --- |
| 版本 / release | 新 release、breaking change、deprecated API | 官方 changelog、repo release | 高 |
| 价格 / 限额 | pricing page 变化、套餐变化 | 官方 pricing、合同 | 高 |
| license | license 文件变化、模型条款变化 | repo、model card、legal docs | 高 |
| 安全 | CVE、安全公告、依赖变更 | GHSA、NVD、vendor advisory | 高 |
| 模型能力 | 新 benchmark、新模型、新评测 | 论文、官方 eval、本地 eval | 中高 |
| 市场格局 | 融资、收购、产品停服 | 官方公告、行业报告 | 中 |
| 社区活跃 | issue、PR、commit 变化 | repo analytics | 中 |
| 法规政策 | 新规、执法案例、标准更新 | 官方监管、标准组织 | 高 |
| 平台 API | SDK / API / auth 改动 | 官方 docs | 高 |
| 硬件支持 | driver、CUDA、芯片、云规格 | vendor docs | 中 |

## 11. 结论语气控制

| 证据状态 | 推荐语气 | 禁止语气 |
| --- | --- | --- |
| L1 + PoC + 风险门清楚 | 建议进入设计或实施准备 | 已经验收 |
| L1 充分但无 PoC | 建议 Trial | 可生产 |
| L2 / L3 充分 | 值得继续评估 | 可以采用 |
| 只有 L4 | 作为线索 | 结论明确 |
| 只有推论 | 可能、需要验证 | 已证明 |
| 缺当前查证 | 截至已查资料 | 最新、当前 |
| 缺 owner | 建议讨论 | 已拍板 |

## 12. 研究到项目的转接

当 research 进入项目链路时，必须把结论转成对应页面：

- 选型建议进入 design / decisions，不留在研究页单独生效。
- PoC 计划进入 TASK 或 acceptance plan。
- 风险进入 risk，不混在结论段。
- 需求变化进入 trace。
- 稳定概念进入 concepts。
- 来源摘要进入 articles。
- 可复用方法进入 skills / templates / governance。

研究页可以链接这些页面，但不能替代它们。

## 13. 采用结论示例口径

### Adopt 示例

> 当前证据支持进入设计 / 实施准备。核心能力由 L1 来源确认，关键风险门没有 blocker，目标约束已有 PoC 或等价运行证据。仍需在项目决策页完成 owner、成本和验收边界确认。

### Trial 示例

> 值得做小范围 PoC。资料显示方向有价值，但缺目标环境验证或部分风险门未闭合。本轮不能写成生产可用。

### Assess 示例

> 建议继续观察并补证据。当前材料足以说明方向存在，但关键事实仍依赖后续 release、价格、license、benchmark 或 owner 确认。

### Hold 示例

> 当前不建议投入实施。阻断点是明确的风险、成本、license、维护或场景不匹配；若解锁条件变化，可以重新评估。

### Blocked 示例

> 暂不能判断。缺少关键一手来源、权限、样本、当前查证能力或决策 owner。

## 14. 研究报告最终回复清单

- 是否说明查证日期。
- 是否说明最强证据和最弱环节。
- 是否说明行动等级。
- 是否说明不能上推到哪里。
- 是否说明刷新触发。
- 是否说明沉淀入口。
- 是否说明未读或不可访问来源。

## 15. 细粒度 research 复核项

- 是否把调研对象命名到足够具体，避免把技术、产品、公司和赛道混在一起。
- 是否写清当前研究要服务的决策，而不是泛泛学习。
- 是否明确不做项，避免研究无限扩大。
- 是否列出必须当前查证的事实。
- 是否对每个关键结论标注证据等级。
- 是否把官方声明和第三方评价分开。
- 是否把开源活跃度和商业成熟度分开。
- 是否把 Star、下载量、融资额当作信号而不是结论。
- 是否检查 license、模型条款或服务条款。
- 是否检查安全公告、供应链、依赖和构建风险。
- 是否检查数据、隐私、日志保留和训练使用边界。
- 是否检查价格、限额、SLA 和退出成本。
- 是否检查运行环境、硬件、账号、地域和权限要求。
- 是否检查替代方案，而不是只研究一个候选。
- 是否检查目标约束下的集成成本。
- 是否区分 demo、PoC、试点和生产。
- 是否写清 PoC 的成功标准。
- 是否写清 PoC 的失败退出条件。
- 是否记录失败样本，而不是只展示成功样本。
- 是否写清 benchmark 是否可复现。
- 是否写清模型评测和业务指标的关系。
- 是否说明当前结论的刷新触发。
- 是否说明哪些事实可能在短期内变化。
- 是否说明哪些风险是 blocker，哪些只是 watch。
- 是否说明行动等级为什么不是更高或更低。
- 是否说明沉淀落位。
- 是否触发 knowledge-linking。
- 是否需要进入 decisions。
- 是否需要进入 design。
- 是否需要进入 risk。
- 是否需要进入 TASK 或 acceptance。
- 是否需要进入 concepts 或 articles。
- 是否需要补 template 或 skill。
- 是否有当前无法查证但影响判断的事实。
- 是否把无法查证写成 blocked，而不是猜测。
- 是否把建议写成用户可执行下一步。
- 是否写清人工确认边界。
- 是否写清本轮没有覆盖的来源。
- 是否避免把旧记忆当当前事实。
- 是否避免把用户假设当研究结论。
- 是否避免把单个来源的营销语言复制成判断。
- 是否避免把“行业趋势”写成“本项目应该做”。
- 是否避免把“技术可行”写成“业务值得做”。
- 是否避免把“可买到”写成“可合规采购”。
- 是否避免把“开源可用”写成“维护可控”。
- 是否避免把“模型很强”写成“业务效果更好”。
- 是否避免把“成本低”写成“总成本低”。
- 是否避免把“社区活跃”写成“长期稳定”。
- 是否避免把“PoC 通过”写成“验收通过”。

## 16. 完成判定

research-capability 的完成状态固定为：

- `ready for learning`：资料、概念边界和主要来源清楚，适合学习。
- `ready for comparison`：替代方案、风险门和证据等级清楚，适合比较。
- `ready for trial`：PoC 目标、样本、指标、成功标准和失败退出清楚。
- `ready for adoption decision`：L1 证据、风险门、PoC 或等价运行、owner 和项目入口都清楚。
- `not ready`：缺当前事实、缺关键来源、缺风险门、缺 owner 或只剩推论。

最终报告必须写明自己处在哪个状态。

## 17. research 失败判定表

出现以下任一情况，研究结论必须降级或判为 `not ready`：

- 没有研究合同。
- 没有关键问题。
- 没有证据等级。
- 没有当前查证日期。
- 没有风险门。
- 没有行动等级。
- 没有刷新触发。
- 没有沉淀落位。
- 把 L4 线索写成 L1 事实。
- 把旧 release 当当前版本。
- 把宣传语当技术结论。
- 把 Star 当采用依据。
- 把 PoC 通过当生产验收。
- 把技术可行当业务值得做。
- 把价格可见当总成本可控。
- 把开源可用当许可可用。
- 把模型 benchmark 当业务指标。
- 把单一供应商资料当行业结论。
- 把无法查证写成 confirmed。
- 把用户假设写成研究发现。

补充失败项：

- 没有说明调研对象版本。
- 没有说明目标读者。
- 没有说明决策成本。
- 没有说明替代方案。
- 没有说明集成成本。
- 没有说明维护成本。
- 没有说明退出成本。
- 没有说明测试样本。
- 没有说明失败样本。
- 没有说明 benchmark 局限。
- 没有说明 license 局限。
- 没有说明安全局限。
- 没有说明隐私局限。
- 没有说明合规局限。
- 没有说明供应链局限。
- 没有说明平台锁定。
- 没有说明人工确认。
- 没有说明后续刷新人或入口。
- 没有说明哪些结论只是推论。
- 没有说明哪些建议不能立即执行。

最终补充失败项：

- 没有把学习结论和采用结论分开。
- 没有把技术成熟和组织可落地分开。
- 没有把一次运行结果和可重复结果分开。
- 没有把供应商承诺和合同保障分开。
- 没有把模型能力和产品体验分开。
- 没有把开源项目健康和本地维护能力分开。
- 没有把短期试验和长期运营分开。
- 没有把研究建议和项目任务分开。
- 没有把证据缺口和后续任务分开。
- 没有把 blocked 与 hold 分开。

确认交付前再问自己：这份研究如果一个月后被复用，读者能不能知道哪些事实可能过期、哪些结论只是推论、哪些建议需要 PoC、哪些风险需要人工确认。不能回答这些问题，就还不是合格的采用依据。

研究产物的价值是帮助后续决策减少不确定性，而不是把不确定性包装成确定结论。任何没有证据等级、没有刷新触发、没有风险门、没有行动等级的研究，都只能作为资料草稿保存，不能作为采用依据。

如果用户只是想学习，输出概念边界和来源；如果用户要选型，输出比较矩阵和风险门；如果用户要采用，必须输出行动等级、PoC 或等价证据、owner 和项目落位。三者不能混写。

当研究发现项目本身的需求、设计或验收条件不清楚时，先把不确定性回写到 trace、decision、risk 或任务入口；研究只能暴露不确定性，不能替项目 owner 完成拍板。

如果研究读者必须靠追问才知道证据等级、行动等级、风险门、刷新触发和未覆盖边界，这份研究就应该判为 needs-work，而不是作为正式依据。

合格研究必须让读者少猜证据、少误判时效、少把建议当决策；做不到这一点，就先改研究合同。
如果为了采纳研究必须重新核对所有来源，说明研究没有完成证据分层和行动转译职责。
如果读者看完仍不知道该试、该等、该停还是该补证据，也说明研究尚未完成。
合格 research 的最小承诺是：减少误采纳、减少旧事实复用、减少无证据建议。
因此，reviewer 应优先审查当前查证、证据等级、风险门、行动等级和刷新触发，而不是优先评价报告篇幅或资料数量。
报告篇幅只在证据合同成立之后再优化。
若两者冲突，证据合同优先。
Review priority: evidence first, action level second, writing polish third, and never the reverse.
Stop if evidence is unclear.
Evidence remains the gate.
No exception.
Do not ship unclear evidence.
Research stops on unclear evidence. When evidence is unclear, the correct output is a lower action level, a sharper evidence request, or a blocked status.

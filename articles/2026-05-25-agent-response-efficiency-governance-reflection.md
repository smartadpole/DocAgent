# Agent 响应效率治理反思

## 来源

本页来自 2026-05-25 对 重治理主控工程、当前模板库、子工程 子工程和 子工程 的 agent 规则、技能和工作流对比分析。

这不是某个研发项目的执行计划，而是对这套文档 / agent 工程自身运行方式的反思。它先作为知识沉淀保留；只有后续明确拍板后，才进入 [[WORKFLOW]]、[[AGENTS]]、[[POLICY]] 或具体技能页。

## 一句话总结

重治理主控工程 的慢主要不是脚本执行慢，也不是单纯无用阅读导致；它的主体成本来自主控治理系统为了保证 issue 分析、证据分层、文档沉淀和状态闭环而必须执行的工作。但当前仍有可优化空间：需要把“快速诊断”“治理沉淀”“验收关闭”“规则升级”显式分层，让系统既功能完整，又更早给用户清晰反馈。

## 关键观察

- 重治理主控工程 的规则入口接近模板库主控层，但工作项实体更多：约 321 个 Markdown、75 个 TASK、24 个 EP、31 个 FP。
- 重治理主控工程 的 `AGENTS`、`WORKFLOW`、`issue-analysis` 和 `work-item-auto-decomposition` 共同形成重启动链；强约束词密度高，简单问题也容易触发完整主控流程。
- 默认检查脚本不是主要瓶颈：`check_project_docs.py` 约 2.3 秒，`check_work_item_matrix.py --strict` 约 0.14 秒。
- 子工程 虽然仓库更大，但多数规则按目录局部加载；只有命中主控 work item 或外部验收时才进入较重的主控协调规则。
- 子工程、子工程、子工程 的规则触发面更窄，通常不会把简单问题升级成完整治理闭环。

## 具体实例复盘

用户举例的“定位某业务单元后续处理未触发原因”耗时约 12 分 53 秒。过程里真正的 issue root cause 定位并不需要这么久：

- 某业务单元已经 dispatch 到 上游准备阶段。
- 调度顶层 task 显示 `Completed`。
- task 列表里没有后续“处理写入”任务。
- 父 flow 日志显示 `skipped 某业务单元`。
- 上游准备阶段 业务结果是 `failed`。
- 失败点是 `输入产物构建 failed`，`输入 manifest=null`。

所以核心结论可以很快得出：不是下游服务没启动，也不是没进批次，而是 上游准备阶段 的 输入产物构建 失败后没有可消费的 输入 manifest，后续 下游处理写入 被调度跳过。

真正耗时的是后半段治理闭环：新增 ISSUE、更新 TASK、同步测试报告、状态、worklog、risk、关系矩阵，再跑结构检查和文档检查。也就是说，它把“请分析原因”自动扩大成了“完成主控仓库事故沉淀和状态闭环”。

## 成本拆分

这类工作不能简单判成“慢就是坏”或“慢都必要”。更客观的拆分是三类：

### 必要成本

这些成本支撑的是主控文档系统的核心价值，不能为了提速删除：

- **事实源分层**：区分 调度顶层状态、上游准备阶段 业务状态、下游处理写入 是否被调度、DB readback 是否产生。
- **原始现象保真**：先保留用户看到的“后续处理未触发 / 截图无处理写入条”，再用日志、API、artifact 和 task 状态解释。
- **证据闭环**：不能只凭 `Completed` 或单一截图下结论，要查 task、log、artifact、上游 run 和父 flow 决策。
- **主控沉淀**：已经确认的新现场问题需要落到 issue、TASK、报告、状态、worklog、risk 和关系矩阵，避免后续误判状态。
- **结构检查**：关系矩阵和文档链接检查能防止“文档写了但系统读不懂”。

这些工作会让任务变慢，但属于功能完整性的一部分。

### 可优化成本

这些成本不是完全无用，但可以通过流程分层降低体感延迟：

- **启动读取过重**：一开始就读取完整治理链，会拖慢首次反馈。
- **模式边界不清**：诊断已经完成后，没有明确告诉用户“现在进入沉淀闭环”。
- **技能触发叠加**：issue-analysis 和 work-item-auto-decomposition 容易同时触发，使单个 issue 进入完整工作项系统流程。
- **检查时机偏后**：把所有沉淀、修链、检查集中到最后，用户难以判断当前是在分析还是在收尾。
- **缺少阶段性输出**：根因确认后没有先输出短结论和证据摘要，再继续文档动作。

这些不是要取消，而是要重新排序和显性化。

### 应避免成本

这些如果出现，就是真正需要修的低效：

- 为了防止违规而读取与当前事实链无关的大量页面。
- 在没有沉淀授权或沉淀必要性时，自动创建正式 issue / TASK / 状态更新。
- 把规则候选误放进项目待办或项目状态，让知识沉淀变成项目执行项。
- 把文档系统的完整闭环伪装成“仍在分析”，导致用户误解进度。

## 问题定义

当前模板库已经很擅长避免漏沉淀、误关闭和证据上推，但还缺少一个明确的“响应模式分层”：

- 简单定位问题和正式验收问题使用相近的前置读取负担。
- 只读分析、主控收口、文档回写、验收闭环、规则反哺之间的模式切换不够显式。
- agent 为了避免违反规则，倾向先读完整治理链，再开始输出，导致用户感受到“几分钟才开始反应”。
- 轻量批处理模式只覆盖大量同类材料，不覆盖“单个简单问题的快速诊断”。

因此，真正要优化的不是把主控沉淀砍掉，而是让 agent 在每轮开始时先判定本轮目标：

- 只需要定位事实？
- 需要 issue 分析并沉淀？
- 需要验收或关闭？
- 需要规则升级？

不同目标应该使用不同的读取范围、输出节奏和收尾动作。

## 建议方向

在不削弱证据边界、主控职责和提交闭环的前提下，增加一层可解释的减载机制，让 agent 能先快后重。

### 快速诊断模式

适用：

- 用户问“为什么慢”“在哪里”“差异是什么”“先分析一下”。
- 当前轮不要求改文档、不要求验收、不要求关闭状态、不要求提交。
- 结论不会直接改变项目状态、规则、自动写入边界或验收结论。

最小动作：

- 读取当前仓库入口规则和最相关的 1 到 3 个事实源。
- 能用命令快速量化的，优先量化。
- 输出 `confirmed / likely / possible / blocked` 分级结论。
- 若发现需要长期沉淀，再提示应升级到计划沉淀或规则升级，不在未授权时扩大写入。

禁止：

- 不把快速诊断写成项目级完成。
- 不关闭 EP / TASK / FP / Gate。
- 不把历史报告、handoff 或局部脚本结果当成本轮验收完成。

### Issue 分析 + 沉淀模式

适用：

- 用户要求定位 issue，并且结论有长期项目价值。
- 已经确认是现场问题、复验失败、实施偏差或验收阻塞。
- 需要后续 owner、子工程、验收或发布节点继续消费该结论。

最小动作：

- 快速给出根因 checkpoint，再进入沉淀闭环。
- 将 issue 事实写入单一信息源，并同步相关 TASK / report / status / worklog / risk / matrix。
- 保留证据边界：哪些是 confirmed，哪些是 likely，哪些还需人工或子工程确认。
- 跑必要检查，并把检查失败修到可交付状态。

禁止：

- 不把沉淀过程省成“最终回复里说一下”。
- 不把局部 issue 沉淀直接升级成 Gate 准出或 TASK 完成。
- 不在根因已确认前批量改状态。

### 沉淀候选模式

适用：

- 用户明确说“沉淀下来”“形成升级计划”“作为反思和计划记录”。
- 当前结论有长期价值，但还没有拍板为新硬规则。

最小动作：

- 优先写入 `articles/` 或合适的知识沉淀入口。
- 若已经明确会改变执行方式，再作为候选回链到 [[WORKFLOW]]、[[AGENTS]]、[[POLICY]] 或相关技能。
- 补写 [[log]]，记录当前只沉淀候选，不直接升格为硬规则。

禁止：

- 不直接把候选内容写入 [[POLICY]] 或 [[AGENTS]]，除非用户明确要求升级为规则，或内容已经满足规则层准入。
- 不把未验证的优化方案伪装成已经生效。

### 验收关闭模式

适用：

- 用户要求验收、复验、关闭、准出或判断 `done`。
- 结论会影响 TASK / EP / FP / Gate / release 状态。

最小动作：

- 先声明验收对象：handoff / artifact 包、代码实现、联调闭环还是 Gate 准出。
- 按 local validation、service-side validation、end-to-end validation 分层检查。
- 如果涉及参数、配置、profile、retry context、采样或业务对象范围，至少验证一个非默认值或边界值。
- 缺证据时只能写 `review / partial / blocked`，不能写完整闭环。

禁止：

- 不把 issue root cause 分析等同于验收关闭。
- 不把子工程 handoff 或历史报告直接当作本轮独立验证。

### 规则升级模式

适用：

- 用户要求把候选变成规则。
- 同类问题已多轮复现，且旧规则无法承接。
- 需要改变默认读取顺序、自动写入边界、收尾规则或 agent 行为约束。

最小动作：

- 按 [[WORKFLOW#0.2.1 收尾怎么执行]] 和规则改动守卫读取 [[AGENTS]]、[[POLICY]]、[[WORKFLOW]]。
- 先判断是改旧规则、补澄清，还是新增模式。
- 同步入口、log 和必要模板。

禁止：

- 不用“提速”为理由弱化原有验收、证据、主控 / 子工程边界和提交闭环。

## 判定表

| 用户意图 | 推荐模式 | 首次反馈目标 | 是否默认改文档 | 是否默认跑矩阵 / 文档检查 |
| --- | --- | --- | --- | --- |
| “为什么 / 在哪 / 先分析” | 快速诊断模式 | 先给根因候选和证据边界 | 否 | 否 |
| “分析并沉淀 issue” | Issue 分析 + 沉淀模式 | 先给根因 checkpoint，再进入沉淀 | 是 | 是，触及工作项时必须跑 |
| “验收 / 关闭 / 准出” | 验收关闭模式 | 先声明验收对象和证据层级 | 是 | 是 |
| “把这个规则化 / 以后都这样” | 规则升级模式 | 先给规则改动守卫和冲突判断 | 是 | 视改动范围 |
| “沉淀这个想法 / 作为反思” | 沉淀候选模式 | 先判断知识层还是规则层 | 是，优先知识沉淀 | 通常否 |

## 体验优化目标

功能完整和高效不是对立关系。合理目标不是把 12 分钟压成 1 分钟，而是把 12 分钟拆成可理解的阶段：

1. **1 到 3 分钟**：给出当前最可信的根因候选、证据和下一步验证点。
2. **根因确认后立即 checkpoint**：告诉用户“分析结论已形成，现在进入沉淀 / 验收 / 规则升级”。
3. **后续治理闭环**：继续完成 issue、TASK、报告、状态、risk、矩阵和检查。
4. **最终回复**：区分诊断结论、沉淀动作、验证边界和下一步。

这样总工作量不一定少很多，但用户能清楚看到：哪些时间花在分析，哪些时间花在系统治理闭环。

## 后续动作

- 先保留为知识沉淀和规则候选。
- 若后续确认要落地，把快速诊断、Issue 分析 + 沉淀、沉淀候选、验收关闭、规则升级几种模式写成 [[WORKFLOW]] 中的流程段落。
- 检查 [[skills/issue-analysis/SKILL]] 是否需要增加“快速分析”分支，避免所有 issue 类问题都默认进入完整主控分析。
- 必要时在 [[README]] 或 [[INDEX]] 的治理 / 研发方法入口补一句模式分层，避免新 agent 只看到重路径。
- 回归确认新模式不会绕过文档沉淀、验收分层、非默认参数验证、主控 / 子工程只读边界和 commit 闭环。

## 当前结论

本页目前是知识沉淀和规则候选，不是已经生效的流程。当前判断是：重治理主控工程 的慢有相当一部分是主控系统功能完整性所必需，但不是所有体感慢都不可优化。后续如果要真正改变 agent 默认行为，应进入规则升级模式，再修改 [[WORKFLOW]]、[[AGENTS]]、[[POLICY]] 或相关技能。

# Codex Goals 专题调研

- 关联概念：[[concepts/codex-goals]]、[[concepts/harness-engineering]]

## 一句话总结

Codex Goals 的本质不是“让模型自己一直跑”，而是给当前线程加上一份持久的完成契约：目标持续存在，但是否完成必须由证据决定。

## 核心判断

这份材料最值得记住的判断有三条：

1. Goal 适合“终点清楚、路径不清楚”的长时工作，例如性能调优、flaky test 调查、benchmark 驱动优化、复杂迁移和研究复现。
2. Goal 不是全局 memory，也不是仓库级规则；它是线程级状态，作用是让 Codex 在多轮之间始终记得终点线。
3. 强 Goal 的关键不在于写得更长，而在于把结果、证据、约束、边界和阻塞停止条件写清楚。

## Goals 是什么

按这份译稿的定义，Goals 是 Codex 中的持久目标。和一次性 prompt 不同，Goal 不只要求 Codex “做下一步”，而是要求它“持续工作，直到某个结果成立，或者被证据证明暂时无法继续”。

用更工程化的话说，Goal 像一个线程内的完成契约：

- `结果`：最终什么状态必须成立
- `证据`：由哪些测试、benchmark、日志、产物或材料证明
- `约束`：哪些东西不能回退
- `边界`：允许动哪些文件、服务、工具和输入
- `停止条件`：什么时候应暂停、清除、总结阻塞，而不是继续空转

它解决的不是“模型会不会做”，而是“模型在多轮推进中会不会丢掉真正的终点”。

## 和普通 Prompt 的区别

最短对比如下：

- `Prompt`：请求 -> 工作 -> 汇报 -> 等下一轮
- `Goal`：工作 -> 检查证据 -> 继续或完成

当你发现自己反复在说下面这些话时，说明任务已经更像 Goal，而不是普通 prompt：

- 继续。
- 再试一种修复路径。
- 重新跑一次 benchmark。
- 现在检查测试。
- 一直推进，直到真的完成。

这时真正需要持久化的不是更多上下文，而是“完成的定义”。

## 什么时候适合用

适合的任务：

- 性能优化：有明确指标阈值
- flaky test 调查：要么修好，要么给出证据化阻塞解释
- 依赖迁移：要跑完构建、测试和回归
- 多步骤重构：目标和约束明确，但下一步取决于刚发现的事实
- 研究复现：需要按主张清单、证据等级和剩余不确定性来交付

不适合的任务：

- 一行代码改动
- 简单解释或短审查
- “把它变更好”这类没有完成条件的模糊请求
- 明显需要人工先裁定范围、指标或约束的任务

## 一个强 Goal 的六要素

这份材料里最实用的部分，是把强 Goal 拆成六件事：

1. `结果`：完成时什么必须成立
2. `验证面`：用什么来证明结果
3. `约束`：哪些性质不能回退
4. `边界`：允许使用哪些文件、工具、数据或资源
5. `迭代策略`：每次尝试后，下一步怎么选
6. `阻塞停止条件`：什么时候该停并报告，而不是继续试

可以复用的骨架是：

```text
/goal <期望的最终状态>，由 <具体证据> 验证，同时保持 <约束>。
只使用 <允许的输入、工具或边界>。
每次迭代之间，记录 <本次改动、证据变化、下一步最值得尝试的行动>。
如果被阻塞或没有有效路径，停止并报告 <已尝试路径、已有证据、阻塞点、下一步所需输入>。
```

## 生命周期和控制面

这份材料给出的命令入口是：

- `/goal`：查看当前 Goal 或设置 Goal
- `/goal pause`：暂停
- `/goal resume`：恢复
- `/goal clear`：清除

它强调几个边界：

- Goal 可以活跃、暂停、完成，或者因为预算受限而停止
- 自动继续是事件驱动，不是无脑循环
- 只有线程空闲、Goal 活跃、预算允许、没有用户输入排队时，Codex 才会继续推进
- 完成必须经过证据审计，不能因为“看起来差不多”就收尾

这里最关键的架构判断是：Goal 的作用域在当前线程，不在全局 memory，也不在项目级指令。

## 为什么这对 Agent Harness 重要

把 Goals 放进 [[concepts/harness-engineering]] 的框架里看，会更清楚它的价值：

- 它不是规则层替代品：AGENTS、技能、权限、测试和 workflow 仍然要存在。
- 它不是 memory 替代品：稳定偏好和团队真相源仍然应优先文件化。
- 它补的是“持续推进层”：当任务要跨多轮时，线程需要一个可审计的完成契约。

所以 Goals 更像 Harness 里的一个中间层：

`prompt -> goal contract -> tools / workflow / evidence -> completion audit`

这个位置很重要。没有 Goal，长任务容易退化成“每轮都重新对齐目标”；只有 Goal、没有证据层，又会退化成“持续忙碌但不知道算不算完成”。

## 对当前 wiki 的启发

这份专题对当前文档库最有价值的不是命令本身，而是几条结构性判断：

1. `Goal` 应被理解为线程级完成契约，而不是新一层全局规则。
2. 长任务的提示词不应只说“继续”，而应提前把证据面、约束和阻塞停止条件写出来。
3. 复杂调研、复现和修复任务如果要长期委托给 Codex，应该把“完成的审计面”前置，而不是靠最后补救。
4. Goals 和 [[response-mode-routing]] 并不冲突：前者定义线程终点，后者定义本轮应该走快速诊断、知识沉淀、验收关闭还是规则升级。

## 可直接复用的例子

### 性能优化

```text
/goal 将 checkout 的 p95 延迟降低到 120 ms 以下，并由 checkout benchmark 验证，同时保持正确性测试套件通过。只使用 checkout 服务、benchmark fixtures 和相关测试。每次迭代之间，记录改了什么、benchmark 显示了什么，以及下一步最值得尝试的实验。如果 benchmark 无法运行或没有有效路径，停止并报告已经尝试的路径、已收集的证据、阻塞点，以及继续推进所需的下一个输入。
```

### flaky test 调查

```text
/goal 持续处理 checkout 的 flaky 测试，直到要么以证据修好它，要么明确说明阻塞进展的真实原因。由复现记录、相关日志和测试结果验证，同时不扩大公共 API 变更范围。每次迭代之间，记录复现条件、假设变化和下一步最高价值检查项。如果当前环境无法稳定复现，停止并报告已尝试条件、缺失证据和解锁下一步所需输入。
```

### 研究复现

```text
/goal 使用可获得的论文材料和本地资源，产出最强的、有证据支撑的复现。尝试主要结果，在可行处验证输出，最终交付一份报告，区分已确认发现、近似重建、被阻塞主张和剩余不确定性。
```

## 风险和注意点

- 不要把 Goal 写成泛目标，例如“改进系统”“重构一下”。
- 不要把预算耗尽误当成完成。
- 不要让 Goal 代替人工裁定：指标、回退边界和允许动的范围，最好先由人定清楚。
- 不要把近似证据包装成精确完成，尤其是研究和复现类任务。
- 这份本地材料提到的版本门槛是 `Codex 0.128.0`；这属于来源中的时点信息，后续可能漂移，实际可用性应以当前 Codex release / docs 为准。

## 当前结论

如果只压成一句话，Codex Goals 代表的是一种新的协作单元：

它让“把一个问题交给 Codex”从一次性交办，变成带终点、带证据、带暂停恢复能力的持续工作契约。

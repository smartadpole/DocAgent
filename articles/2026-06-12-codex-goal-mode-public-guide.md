# Codex Goal 模式使用教程：让长任务有终点、有证据、有停止条件

Codex Goal 模式适合把“请继续做下去”升级成一个可验证的长任务契约。它的价值不只是让 Codex 多跑几轮，而是让 Codex 在长时间工作时始终知道：目标是什么，哪些证据说明完成，哪些边界不能越，什么时候必须停下来。

这篇教程面向已经会使用 Codex 的开发者、产品技术负责人和 AI coding agent 使用者。你可以把它当成一份对外发布的操作指南。

## 1. 先看一个实际开发场景

一个团队要交付一页可外发的报告页面。需求看起来很小：

```text
帮我把这份报告做成 HTML，并导出 PNG / PDF。
```

如果只用普通 prompt，Codex 可能先完成页面主体，但后面很容易漏掉这些关键事项：

- HTML 页面能看，但 PDF 打印分页不对。
- PNG 来自另一套截图脚本，和 HTML 内容不同源。
- 桌面端正常，移动端出现横向滚动。
- 页面底部混进了内部调试信息，不适合对外发布。
- 做完后只说“已完成”，但没有给出截图、导出文件和检查结果。

更适合 Goal 的写法是：

```text
/goal 完成报告页的外发导出闭环：HTML 页面只展示最终读者需要的信息，PDF 和 PNG 必须从同一个 HTML 源生成，桌面端和移动端都不能出现横向溢出。每轮用 Playwright 导出 PDF / PNG，并检查 scrollWidth、页面标题和关键文案；如果素材缺失、导出失真或需要人工确认发布口径，暂停并报告已有证据和缺口。
```

这个案例的重点不是“做一个页面”，而是把完成标准说清楚：

- **目标状态**：外发 HTML 可读，PDF / PNG 同源导出。
- **验证循环**：每轮导出、截图、检查宽度和关键文案。
- **停止边界**：素材缺失、发布口径不清或导出失真时停下来。

这就是 Codex Goal 最适合发挥作用的地方：任务不一定很大，但它需要跨多步保持同一个完成标准。

## 2. Goal 模式是什么

在 Codex 里，Goal 模式可以给当前任务设置一个持久目标。官方文档的核心说法是：当一个任务需要 Codex 跨多轮持续工作，并且有可验证的停止条件时，可以使用 `/goal`。

普通 prompt 通常是：

```text
用户提出请求 -> Codex 执行一轮 -> 汇报结果 -> 等待下一轮指令
```

Goal 模式更像：

```text
用户设定目标 -> Codex 执行 -> 检查证据 -> 继续 / 暂停 / 完成 / 阻塞
```

官方提示文档还说明，Goal 文本会同时充当起始 prompt 和完成标准。也就是说，Goal 写得越清楚，Codex 越容易判断自己下一步该做什么，以及什么时候应该停止。

## 3. 什么时候应该使用 Goal

适合使用 Goal 的任务，通常有三个特征：

1. **目标清楚**：你知道最终想达到什么状态。
2. **路径不完全清楚**：下一步要根据测试、日志、代码、运行结果或中间发现来决定。
3. **可以验证**：有测试、benchmark、截图、报告、构建结果、验收用例或其他 artifact 能证明进展。

典型场景：

- 代码迁移：例如从旧框架迁移到新框架，并保持功能或视觉一致。
- 大型重构：每个 checkpoint 都可以跑测试或构建。
- 性能优化：目标是把某个指标降到阈值以下。
- flaky test 调查：要么修复，要么证明当前环境无法稳定复现。
- Prompt / eval 优化：持续迭代，直到评测指标达标或遇到需要人工判断的边界。
- 原型打磨：依据计划文件持续构建，直到可运行、可演示、可验证。

不适合使用 Goal 的任务：

- 一次性解释、翻译、总结。
- 很小的单文件修改。
- “让它更好”“继续完善”这种没有完成标准的模糊目标。
- 一串无关待办的 backlog。
- 需要人先拍板范围、预算、权限或成功标准的任务。

一个好判断是：**Goal 应该比一次 prompt 大，但比一个开放 backlog 小。**

## 4. 基本命令

在支持 Goal 模式的 Codex 界面中，可以使用：

```text
/goal <objective>
```

例如：

```text
/goal Finish the TypeScript migration and keep all tests green.
```

常见控制命令：

```text
/goal
/goal pause
/goal resume
/goal clear
```

它们分别用于查看当前 goal、暂停、恢复和清除 goal。

在 CLI 中，官方 slash command 文档说明 goal 文本必须非空，且最长为 4,000 字符；如果说明更长，建议把细节写进文件，再在 goal 里指向该文件。

如果你的 slash command 列表里没有 `/goal`，官方文档给出的方式是启用 `features.goals`：

```toml
[features]
goals = true
```

也可以运行：

```bash
codex features enable goals
```

实际可用性仍以你当前 Codex 版本、界面和团队配置为准。

## 5. Goal Contract：写好 Goal 的实用框架

`/goal` 是 Codex 的产品能力；Goal Contract 是一种写好 goal 的方法。它不是额外工具，也不是官方命令，而是一份启动前的任务契约。

一个好的 Goal Contract 至少包含八项：

1. **目标**：最终要达到什么状态。
2. **完成判定**：什么算 done，什么只能算 partial / review / blocked。
3. **验证面**：用什么测试、命令、benchmark、截图、报告或 artifact 证明。
4. **约束**：哪些行为不能发生，例如不改公共 API、不扩大依赖、不碰生产数据。
5. **允许范围**：Codex 可以读写哪些文件、运行哪些命令、使用哪些工具。
6. **迭代方式**：每轮做什么检查，如何选择下一步。
7. **停止条件**：什么时候必须暂停或汇报，而不是继续探索。
8. **进展记录**：每个 checkpoint 要记录什么，方便你信任长时间运行过程。

## 6. 可复制模板

你可以直接复制下面这段作为 goal 前置说明：

```text
目标：
持续推进 <任务名称>，直到 <期望最终状态> 成立，或者被证据证明暂时无法继续。

完成判定：
- done：<必须满足的测试、指标、构建、报告或人工验收证据>
- partial / review：<只能说明局部成立、仍需复核的证据>
- blocked：<必须停止并需要人工输入的条件>

验证面：
- <要运行的测试、命令、benchmark、UI 检查、报告或 artifact>
- <哪些证据只能作为辅助参考，不能单独证明完成>

边界：
- 允许：<文件、目录、工具、命令、环境、数据>
- 不做：<禁止项、非目标、需人工确认的动作>

迭代方式：
- 每轮记录：<本轮做了什么、验证结果是什么、下一步是什么>
- 下一步选择：<优先修失败测试、优先缩小复现、优先跑 benchmark 等>

停止条件：
- <权限不足、证据不足、预算耗尽、目标冲突、需要产品/安全/业务裁决等>
```

压缩成 `/goal` 时，可以这样写：

```text
/goal 持续推进 <任务名称>，直到 <完成判定> 成立。每轮使用 <验证面> 检查进展，保持 <约束>，只在 <允许范围> 内修改。若遇到 <停止条件>，暂停并报告已尝试路径、已有证据、缺口和下一步需要的人工输入。
```

## 7. 示例一：代码迁移

弱 goal：

```text
/goal 帮我完成迁移。
```

问题是：它没有说明迁移到哪里、完成标准是什么、如何验证，也没有停止条件。

强 goal：

```text
/goal 将项目从 JavaScript 迁移到 TypeScript。完成标准是应用能在 strict mode 下编译通过，不新增显式 any，现有测试全部通过。优先迁移 src/ 下的运行时代码，不改公共 API，不做无关重构。每个 checkpoint 后运行 npm test 和 npm run typecheck；如果第三方类型缺失或迁移需要改变公共 API，暂停并报告选项。
```

为什么更好：

- 最终状态明确。
- 验证命令明确。
- 修改范围明确。
- 风险边界明确。
- 阻塞条件明确。

## 8. 示例二：性能优化

```text
/goal 将首页 time to interactive 降到 1 秒以内，并保持现有端到端测试通过。每轮只做一个性能假设，记录改动、测量结果和下一步。如果指标无法稳定测量，或者优化会牺牲关键功能，暂停并报告已有证据和建议取舍。
```

这个 goal 的核心不是“优化性能”，而是：

- 指标阈值清楚。
- 每轮实验受控。
- 正确性不能回退。
- 无法测量时停下来。

## 9. 示例三：flaky test 调查

```text
/goal 调查并处理 checkout 流程中的 flaky test。完成标准是能够稳定复现并修复，或给出证据说明当前环境无法稳定复现。每轮记录复现条件、失败日志、假设变化和下一步检查项。不扩大公共 API，不跳过测试。如果 10 次重复运行都无法复现，暂停并报告已尝试条件和仍缺少的证据。
```

这类任务很适合 Goal，因为下一步通常取决于刚刚拿到的日志、失败样本或复现结果。

## 10. 示例四：Prompt / eval 优化

```text
/goal 优化 prompts/qa_prompt.md，直到 eval suite 的准确率达到 92% 以上，或进一步提升需要产品/策略判断。每轮只做最小 prompt 改动，运行 npm run eval:qa，记录失败案例、改动理由和分数变化。不修改 eval 数据集，不为了分数硬编码答案。
```

这里的关键是把“变好”换成了“指标达到阈值”，同时防止 Codex 通过污染 eval 或硬编码答案来达成表面目标。

## 11. 运行中如何管理 Goal

Goal 启动后，不代表你只能等待。你仍然可以继续引导 Codex，但最好用 checkpoint 的方式，而不是不断追加零散指令。

好的运行中反馈：

```text
当前 checkpoint 先只解决 typecheck 失败。不要开始性能优化。每修完一组错误后运行 npm run typecheck 并汇报剩余错误类型。
```

不好的运行中反馈：

```text
再看看别的地方。
```

如果你不确定当前状态，可以输入：

```text
/goal
```

如果方向需要调整，可以暂停：

```text
/goal pause
```

如果任务已经完成、阻塞或方向改变，可以清除：

```text
/goal clear
```

## 12. 状态报告应该长什么样

长任务最怕“看起来一直在忙，但不知道是否更接近完成”。建议要求 Codex 用固定格式汇报：

```text
当前 checkpoint：
已完成：
已验证：
仍未完成：
阻塞 / 风险：
下一步：
```

更严格一点：

```text
状态：done / partial / review / blocked
证据：
不能上推的证据：
下一步需要：
```

这能防止把“跑过一个命令”“日志看起来正常”“某个子步骤完成”误当成整个 goal 完成。

## 13. 最常见的误用

### 误用一：把 Goal 当成更长的 prompt

如果只是写：

```text
/goal 继续完善这个项目
```

Codex 会缺少完成标准。更好的写法是说明最终状态、验证方式和停止条件。

### 误用二：把 Goal 当成自动关闭器

Goal 可以帮助 Codex 持续推进，但不能替你做产品、工程、安全或业务层面的最终裁决。比如生产发布、验收关闭、API 兼容性变更，仍然需要明确的证据和人工判断边界。

### 误用三：没有停止条件

没有停止条件的长任务容易变成无限探索。你应该提前说明：

- 多少次失败后停。
- 哪些权限缺失时停。
- 哪些风险出现时停。
- 哪些决策需要人来拍板。

### 误用四：把辅助证据当完成证据

服务能启动、日志没有明显报错、某个测试通过，都可能只是辅助证据。真正的完成证据必须回到 goal 的完成判定。

### 误用五：一条 Goal 塞进太多无关任务

Goal 应该围绕一个明确目标，而不是一个杂乱 backlog。多个目标最好拆成多个阶段或多个 goal。

## 14. 启动前检查表

设置 `/goal` 前，先问自己：

- 目标是否能用一句话说清？
- 是否有明确完成标准？
- 是否有验证命令或验证 artifact？
- 是否说明了不能改什么？
- 是否说明了允许 Codex 动哪些范围？
- 是否有停止条件？
- 是否要求 Codex 保留 checkpoint 记录？
- 如果目标很难定义，是否应该先用 `/plan` 让 Codex 帮你拆解？

## 15. 一个通用公式

```text
/goal 完成 <一个明确目标>，直到 <可验证完成状态>。使用 <验证命令或 artifact> 检查进展，保持 <约束>，只在 <允许范围> 内修改。每轮记录 <进展和证据>。如果 <停止条件> 出现，暂停并报告 <已有证据、缺口和需要的输入>。
```

## 16. 最短结论

Codex Goal 模式不是“让 Codex 无限自动跑”的按钮。

它更适合被理解为：**给长任务加一条可验证的终点线**。

写好 Goal 的关键是四句话：

1. 我要什么结果。
2. 用什么证明结果。
3. 哪些事情不能做。
4. 到哪里必须停。

只要这四件事清楚，Goal 模式就能把长任务从“反复催它继续”，变成“围绕证据持续推进”。

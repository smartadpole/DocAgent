## 一句话总结

把新信息直接写成计划节点，是“记录”思维；先把它更新进 `状态变量 + 约束关系 + 外部不确定 + 可执行性判断`，再决定是否改计划，才是成熟的系统推理。

## 这不是单一学科问题

这类能力在成熟方法里并不是一门单独知识，而是几条线共同解决：

- **自动规划** 负责把世界表示成 `state + action + precondition + effect + goal`，防止把用户意图误当成已可执行动作。
- **时间约束网络** 负责处理先后顺序、最早 / 最晚时间、可行时间窗，以及“外部时间不确定”。
- **约束规划 / 调度** 负责把任务、资源、时间窗、互斥关系放进统一约束系统，让依赖自动传播。
- **项目调度 / 关键路径** 负责把现实推进中的依赖、工期、强制日期和回推逻辑讲清楚。
- **MBSE / Statecharts / SysML** 负责把结构、状态和约束分视图表达，避免多段笔记各自为政。
- **系统思维** 负责把变量、反馈、延迟、瓶颈和信息流纳入整体，不把问题缩成局部前置条件。

这也是为什么“搬家计划出错”会和旅行、办证、采购、部署、上线、看病、签合同属于同一类问题：它们都不是简单动作清单，而是带状态、权限、资源、时间和外部确认的可执行性问题。

## 各维度能解决什么

### 1. 自动规划：把意图和动作分开

- 核心对象：状态、动作、前提、效果、目标。
- 关键贡献：
  - 用户说“我要 6.15 入住”时，这只是目标或新事实，不等于“保洁已可安排”“首搬已可执行”。
  - 每个动作都应先问：它的前提状态是什么，动作发生后会改变哪些状态。
  - 一旦前提未满足，动作就不能被直接写成当前安排。
- 适合吸收的结构：
  - `事实`
  - `目标`
  - `动作`
  - `前提`
  - `效果`
  - `阻塞`
- 局限：自动规划擅长逻辑结构，但默认对真实世界里的模糊资源、外部不确定和软偏好表达得不够自然。

### 2. 时间约束网络：把“何时可做”从“想什么时候做”里分离出来

- 核心对象：时间点、时间区间、先后约束、外部不确定。
- 关键贡献：
  - “6.15 入住”会改变首次搬运、保洁、签约、钥匙交接、旧房交割等时间窗。
  - 某个动作提前，前置动作不一定只是“也提前”，而是要检查新的时间窗是否仍可满足。
  - 有些约束是确定的，有些约束依赖外部人或外部系统，只能标成 contingent。
- 适合吸收的结构：
  - `最早开始`
  - `最晚完成`
  - `必须先于`
  - `外部确认后才能定`
  - `若 X 延迟则 Y 自动受影响`
- 局限：只用时间网络还不够，因为很多现实问题不是只缺时间，而是缺权限、资源或承诺。

### 3. 约束规划 / 调度：把资源、互斥和容量放进同一个传播系统

- 核心对象：任务、资源、容量、时间窗、互斥、选择变量。
- 关键贡献：
  - 同一时间只有一个搬家公司、一个钥匙持有人、一个工作日窗口，这些都属于资源约束。
  - “保洁要更早”不只是前后顺序问题，也可能碰到“保洁方当天没空”“你本人不在场”“钥匙尚未交付”。
  - 约束传播的价值在于：一个条件变化后，让所有受影响变量自动重新收缩，而不是手工改一串 TODO。
- 适合吸收的结构：
  - `资源可用性`
  - `容量`
  - `互斥`
  - `必选 / 可选`
  - `条件成立时才可排程`
- 局限：形式化程度高，适合高复杂度排程；个人系统里通常不必真的上求解器，但思路值得保留。

### 4. 项目调度 / 关键路径：把“倒推”变成默认动作

- 核心对象：依赖、工期、强制日期、回推、缓冲。
- 关键贡献：
  - 先固定关键节点，再回推其前置链。
  - 任何强制日期都会对上游动作形成约束传播，不应只在终点页新增一条记录。
  - “可拿钥匙”这种条件应被视为强约束节点，而不是描述性备注。
- 适合吸收的结构：
  - `终点里程碑`
  - `倒推链`
  - `强制日期`
  - `缓冲`
  - `关键依赖`
- 局限：传统项目调度对现实生活里模糊信息和外部不确定表达偏硬，通常需要和状态模型、风险表一起用。

### 5. MBSE / Statecharts / SysML：把状态、结构和约束分视图表达

- 核心对象：状态机、结构视图、参数约束、接口关系。
- 关键贡献：
  - 同一系统可以同时有状态视图、流程视图、资源视图、约束视图，不应全部混在一段线性描述里。
  - 状态和动作必须分开：状态回答“现在成立什么”，动作回答“执行什么会改变状态”。
  - 当系统变复杂时，应让不同视图共享同一事实，而不是每份计划各写一遍。
- 适合吸收的结构：
  - `状态变量表`
  - `状态转移`
  - `约束关系`
  - `结构视图`
  - `视图间单一信息源`
- 局限：对个人计划来说直接上 SysML 太重，但“分视图、单一信息源、状态优先”很有价值。

### 6. 系统思维：把局部前置条件升级为全局变量传播

- 核心对象：变量、反馈、延迟、杠杆点、信息流。
- 关键贡献：
  - 有些问题不是“忘了一个前提”，而是根本没有看到系统里的关键变量和耦合。
  - “钥匙”不是孤立事项，它是多个动作的门槛状态；“首次搬运”也不是单动作，而是触发后续保洁、旧房释放、物品分流、休息成本变化的杠杆点。
  - 一条新事实进入系统后，先问它改变了什么变量和边界，而不是先写动作。
- 适合吸收的结构：
  - `关键变量`
  - `反馈环`
  - `延迟`
  - `瓶颈`
  - `信息缺口`
- 局限：系统思维擅长找结构，不擅长给出可直接执行的任务模型；需要和前几条方法合并使用。

## 对当前问题最有用的组合方式

如果目标是形成一套跨搬家、旅行、办证、采购、部署、上线都能复用的方法，最值得吸收的不是某一门，而是下面这个组合：

1. **用自动规划定义基本语法**：
   - 状态是什么
   - 动作是什么
   - 前提是什么
   - 效果是什么
2. **用时间约束网络表达时序和外部不确定**：
   - 哪些时间是确定的
   - 哪些时间依赖外部确认
3. **用约束规划表达资源、互斥和容量**：
   - 谁能做
   - 什么资源只在某时间可用
4. **用项目调度做倒推**：
   - 从强制节点往前回推
5. **用 MBSE / 状态机做长期知识沉淀**：
   - 把状态视图和动作视图分开
6. **用系统思维检查漏掉的变量和反馈环**：
   - 有没有遗漏关键状态、信息流或瓶颈

## 可直接吸收到个人方法里的最小模型

最小可用的状态变量通常至少包括六类：

| 变量类 | 问的不是“做什么” | 问的是什么 |
| --- | --- | --- |
| 事实状态 | 不是“要不要搬” | 当前已经确认了什么 |
| 权限状态 | 不是“想不想做” | 谁有权执行、批准或交接 |
| 资源状态 | 不是“理论可做” | 人、钱、车、物、服务、时间槽是否可用 |
| 时间状态 | 不是“目标日期” | 最早 / 最晚窗口、前后依赖、缓冲是否成立 |
| 承诺状态 | 不是“口头提过” | 哪些已被双方确认，哪些只是愿望 |
| 外部不确定 | 不是“默认会有” | 哪些依赖外部回复、审批、物流、系统健康 |

与之配套的信息分类至少包括：

- `confirmed fact`
- `goal / intent`
- `hard constraint`
- `soft preference`
- `assumption`
- `candidate action`
- `blocker`
- `contingent dependency`

## 对当前 wiki 最值得沉淀的结论

最关键的不是“以后多记前置条件”，而是把默认问法换掉：

- 不是先问“下一步做什么”
- 而是先问“这条新信息改变了哪些状态变量、约束关系和可执行性”

也因此，成熟的默认链路应该是：

`新信息进入 -> 归类为事实/目标/约束/假设/动作候选 -> 更新状态变量 -> 做前向/后向约束传播 -> 标出未知和阻塞 -> 判断当前是否可执行 -> 最后才更新计划`

这套方法在本库的治理落点是 [[state-constraint-reasoning]]。

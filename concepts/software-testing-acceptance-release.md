# 软件测试、验收和上线

主入口：[[INDEX]]

相关规则：[[projects/development/plan/test-acceptance-planning-model]]、[[projects/development/acceptance/README]]、[[projects/development/reports/README]]

这页沉淀“测试、验收、上线”的通用软件工程知识。它不记录具体项目服务器、端口、任务编号或运行事实；这些内容应落到项目测试计划、服务台账、具体 issue / TASK / EP / Gate 或测试报告中。

核心原则：

> 环境是证据面，不是荣誉阶梯。测试证明实现，验收裁决事项，上线推广能力；三者相关但不能互相替代。

## 三个动作

| 动作 | 回答的问题 | 典型证据 | 输出 |
| --- | --- | --- | --- |
| 测试 | 实现是否符合某个可检验假设 | 静态检查、单元 / 合同 / 集成 / 系统 / E2E 测试、日志 / API / artifact 读回 | 测试结果、缺陷、覆盖缺口 |
| 验收 | 事项的关闭合同是否满足 | 原 bug 反向用例、代表路径、回归守卫、未验证边界、状态裁决 | done / review / partial / blocked / failed |
| 上线 | 已验收能力能否安全进入目标运行范围 | 版本、配置 readback、服务组健康、监控、回滚、受控发布反馈 | 发布成功、灰度通过、生产确认、暂停或回滚 |

一句话：测试是事实取证，验收是合同裁决，上线是运行推广。

## 环境角色

环境命名应抽象成角色，再由项目文档映射到具体机器、域名、服务组或账号。

| 环境角色 | 主要用途 | 不应承担 |
| --- | --- | --- |
| 开发环境 | 编码、自测、局部服务、fixture、快速反馈 | 生产发布结论 |
| CI 环境 | 自动化检查、单元 / 合同 / 静态测试、构建可重复性 | 真实业务运行裁决 |
| 集成环境 | 多组件联调、接口合同、服务组合 | 生产流量确认 |
| 预发 / 灰度环境 | 贴近生产配置、部署流程、真实依赖、小范围业务验证 | 普通 bug 的默认关闭门槛 |
| 生产环境 | 对真实用户或业务生效，承接上线确认和现场反馈 | 普通研发测试的首轮试验场 |
| 外部依赖 / 读回源 | 数据库、模型服务、第三方 API、湖仓、消息系统等 | 单独代表完整验收环境 |

环境路由的判断顺序：

1. 先看验收对象和关闭合同。
2. 再看哪些证据无法在低风险环境获得。
3. 只有证据需求触发时，才进入更高风险或更真实的环境。
4. 任何环境证据都必须写清“不上推边界”。

## 验收最小要素

- **验收对象**：issue、TASK、EP、FP、Gate、发布节点或业务交付物。
- **验收目标**：要证明的用户可见结果或系统可观察结果。
- **非目标**：本轮明确不证明什么。
- **关闭标准**：哪些证据足够通过，哪些只能 partial，哪些直接失败。
- **证据层级**：代码级、服务侧、端到端、人工确认、生产反馈分别覆盖什么。
- **代表路径**：原 bug 或核心业务出现在哪条路径，验收就至少覆盖该路径或等价路径。
- **回归范围**：哪些历史已验收能力必须复跑，哪些说明不相关。
- **人工确认**：哪些事实只能由业务、法务、运维、客户或 owner 裁决。
- **上推边界**：本事项通过能给父项提供什么输入，不能自动关闭什么。

## 证据层级

| 层级 | 能证明 | 不能证明 |
| --- | --- | --- |
| 代码级证据 | 逻辑分支、类型、格式、局部合同 | 服务实际部署、真实依赖、用户闭环 |
| 本地服务侧证据 | 本机服务组合、fixture、接口、局部 UI/API | 远端配置、灰度批次、生产运行 |
| 目标服务组证据 | 部署版本、运行配置、服务组合、目标环境依赖 | 全量业务准出或生产长期稳定 |
| 端到端证据 | 从触发到最终 artifact / DB / UI / 报表的闭环 | 其他批次、其他租户、长期容量 |
| 生产反馈证据 | 真实现场表现、监控、事故和恢复 | 修复逻辑在所有环境都正确 |

## Bug 修复验收

已发生 bug 的验收必须从原始现象反推测试设计：

1. 保留用户原始可见现象、入口、环境、样本和时间窗口。
2. 把原始现象转成可复跑的失败判据。
3. 设计同场景代表性用例，覆盖同一服务、同一业务路径或同一数据轨道。
4. 优先保留修复前失败、修复后通过的自动化回归守卫。
5. 不能复跑原场景时，明确替代用例差异和不能上推边界。
6. 把修复证据写回 issue、报告、相关 TASK / EP 和测试计划。

## 常见反模式

- 把“跑了测试”当成“验收通过”，但没有关闭标准和未验证边界。
- 把“验收通过”当成“已经上线”，但没有部署、配置、监控和回滚证据。
- 把环境当阶梯，机械要求逐层重跑，而不问证据需求。
- 把生产现场发现的问题默认写成必须在生产复测关闭。
- 把接口请求成功、任务 accepted、页面 200、进程存在或引擎 Completed 当成后台效果或业务成功。
- 把单样本、mock、dry-run 或灰度 smoke 上推成全量业务准出。
- 把人工确认、法务确认、业务 owner 裁决伪装成自动化测试结论。
- 把测试报告当长期事项档案，导致 issue / TASK / EP 自己没有当前裁决。

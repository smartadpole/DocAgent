# 阶段门滚动冻结

## 定义

阶段门滚动冻结是一种复杂研发方案的设计推进方法。

它把“正确的一次写好”定义为：

- 一次性写好全局架构、阶段门、合同骨架、依赖地图和细化规则。
- 按阶段门逐步冻结代码级接口、数据、测试和验收。
- 不在证据不足时把所有后续细节强行写死。
- 不把“后续再说”当成没有全局方案的借口。

它适合多服务、多模块、多阶段、真实环境不完全确定的工程项目。

## 核心原则

- **全局先完整**：先把系统目标、服务边界、端到端链路、阶段门、跨阶段合同和风险归口写清楚。
- **近期先冻结**：当前 Gate 的 P0 功能点和跨阶段主合同必须达到代码级设计。
- **下一阶段并行准备**：不能等当前 Gate 结束才开始设计下一 Gate；当前 Gate 开发期间要并行冻结下一 Gate 的 P0。
- **远期先保骨架**：后续阶段保留目标、依赖、风险和验收骨架，等真实事实充分后再冻结代码级细节。
- **候选项进入实现前必须补齐**：候选功能点一旦进入实现、需要 owner、需要排期或阻塞下一 Gate，就必须补齐依赖、接口、数据、测试、验收和阻塞。

## 不是这两种极端

- 不是一次性写死所有细节：这会把未知字段、未知接口、未知凭据和未知容量假设固化成开发负担。
- 不是走一步看一步：全局架构、阶段门、合同骨架和依赖地图必须先成型，否则多个模块容易各自局部正确、端到端集成失败。

## 最小产物

一次“正确的一次写好”至少要产出：

- **全局架构**：系统边界、服务边界、执行形态和非目标。
- **阶段门**：阶段目标、前置条件、完成定义和回退边界。
- **合同骨架**：跨服务交接对象、状态、幂等、版本、错误语义和生产者 / 消费者。
- **依赖地图**：每个阶段依赖的上游服务、数据、凭据、环境、配置和人工拍板事项。
- **细化规则**：哪些现在冻结，哪些并行准备，哪些进入下一阶段前冻结。
- **测试策略**：当前阶段的代码级测试矩阵，以及后续阶段的验收骨架。
- **风险归口**：无法自动判断的问题进入会议、决策或风险登记，不散落在功能点里。

## 冻结节奏

| 层级 | 应该什么时候冻结 | 冻结到什么程度 |
| --- | --- | --- |
| 当前 Gate P0 | 启动开发前 | 代码级接口、数据、测试、验收和回退 |
| 下一 Gate P0 | 当前 Gate 开发期间 | 真实依赖、样本、字段、失败码和小样本验收 |
| 下下个 Gate | 前一 Gate 启动前 | 代码级设计和验收标准 |
| 远期阶段 | 当前只保留骨架 | 目标、风险、容量、审批和路线图 |

## 候选功能点提升标准

候选功能点提升为实体页或正式开发任务前，至少要回答：

- **依赖**：依赖哪些服务、表、凭据、配置、环境和前置功能点。
- **接口**：输入、输出、状态、错误语义、幂等键和版本字段是什么。
- **数据**：写哪些表、文件或对象存储 URI，是否参与追踪和对账。
- **测试**：覆盖单测、契约测试、mock e2e、小样本真实联调或受控验收中的哪几类。
- **验收**：最小通过标准，失败时如何回滚、补偿或进入待处理队列。
- **阻塞**：哪些事项需要会议、owner、权限或真实环境拍板。

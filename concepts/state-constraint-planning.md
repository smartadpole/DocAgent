# State-Constraint Planning

## 定义

State-Constraint Planning 是一种把计划问题先建模为 `系统状态 + 约束关系 + 外部不确定 + 可执行性判断`，再更新动作安排的方法。

它不把用户说出的意图直接当作可执行计划，而是先回答：

- 这条新信息改变了哪些状态变量
- 它会向哪些依赖传播
- 当前有哪些前提已满足、未满足或仍不确定
- 在当前系统状态下，这个动作到底能不能执行

最短公式是：

`新信息 -> 状态更新 -> 约束传播 -> 可执行性判断 -> 计划更新`

## 它在纠正什么错误

它主要纠正一种高频错误：

> 把“用户表达的意图”直接写成“当前可执行安排”。

常见症状包括：

- 线性记录：你说 A，我写 A；你说 B，我写 B。
- 只补动作，不补状态。
- 只记前置条件，不做全局传播。
- 把愿望、目标、假设和已确认事实混写。
- 明明还缺权限、资源、时间窗或外部确认，却提前写出执行节点。

## 核心组件

### 1. 状态变量

- 事实状态：已确认的现实事实。
- 权限状态：谁能批准、交接、访问、签字、执行。
- 资源状态：人、钱、车、设备、服务、容量、时间槽。
- 时间状态：最早 / 最晚时间、先后依赖、窗口和缓冲。
- 承诺状态：哪些已经双方确认，哪些只是口头提及。
- 外部不确定：天气、物流、审批、对方回复、系统可用性等 contingent 条件。

### 2. 信息分类

- `confirmed fact`
- `goal / intent`
- `hard constraint`
- `soft preference`
- `assumption`
- `candidate action`
- `blocker`
- `contingent dependency`

### 3. 传播关系

- 前向传播：A 成立后，会推动哪些状态发生变化。
- 后向传播：为了实现 B，必须先满足哪些状态。
- 资源传播：某资源被占用或不可用，会卡住哪些动作。
- 时间传播：某窗口提前或延后，会改写哪些前后依赖。
- 权限传播：某批准、钥匙、账号、签约未完成，会阻塞哪些动作。

### 4. 可执行性结论

- `executable`：当前前提已经满足。
- `conditionally executable`：满足若干明确条件后可执行。
- `contingent`：依赖外部不确定，当前只能保留条件计划。
- `blocked`：关键前提未满足，不能排进当前计划。
- `not-in-scope`：和本轮目标无关，不应混入当前执行面。

## 组合来源

这不是一门单独学科，而是多条方法线的组合：

- 自动规划：提供 `state / action / precondition / effect / goal`
- 时间约束网络：处理时间窗和外部时间不确定
- 约束规划 / 调度：处理资源、容量、互斥和条件排程
- 项目调度 / 关键路径：处理倒推、强制日期和缓冲
- MBSE / Statecharts：处理状态视图、结构视图和单一信息源
- 系统思维：处理变量、反馈、延迟和杠杆点

更完整的研究汇总见 [[articles/2026-05-28-state-constraint-planning-research]]。

## 适用场景

- 搬家、旅行、办证、采购、签合同、看病、装修这类生活型计划。
- 上线、发布、迁移、部署、联调、验收这类工程型计划。
- 多方参与、外部确认较多、资源受限、时间窗明显的安排问题。
- 用户只给出目标或新事实，但系统需要判断“现在到底能不能做”的场景。

## 不适用的情况

- 纯信息查询，不涉及动作安排。
- 已经确认好所有状态，只需机械转录。
- 非计划型的知识摘录，不需要可执行性判断。

## 最小检查链

1. 这条信息是事实、目标、约束、假设还是动作候选。
2. 它影响哪些状态变量。
3. 它会向哪些前置、后置、资源、时间或权限依赖传播。
4. 哪些变量已确认，哪些只是愿望，哪些仍 blocked。
5. 当前动作是可执行、条件可执行、contingent 还是不可执行。
6. 只有做完上面这些，才更新计划节点。

## 常见误区

- 把日期变化只当一条新记录，不做倒推。
- 把“能提前拿钥匙”误读成“保洁已经可以安排”。
- 把一段计划写成动作流水，没有状态变量。
- 把一个人的想法写成双方已确认承诺。
- 把未证实的外部配合默认当成会发生。

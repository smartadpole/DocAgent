# Technology Research Transfer

## 能力目标

让目标工程具备技术、开源工程、行业 / AI 赛道和 PoC 调研的统一执行能力：先固定调研合同和证据等级，再给成熟度、风险、行动建议和沉淀落位。

## 可以吸收

- 对象路由：技术概念、开源工程、行业 / AI、PoC、本地源码工程。
- 证据等级：一手事实、权威分析、产业信号、媒体线索、推论和建议。
- 成熟度和行动等级：TRL、Adopt / Trial / Assess / Hold，或 A / B / C / D。
- 风险门：安全、license、供应链、隐私、合规、AI 评测、成本、维护。
- 分支流程：技术专题、开源工程、行业 / AI、PoC 的最小判断链。
- 沉淀守卫：article / concept / skill / template / project 的落位判断和补链要求。

## 只能抽象吸收

- AcknowledgeBase 的调研文章、概念页、模板和 source matrix 只能作为方法参考。
- 某个开源项目、公司、行业、模型或产品的结论只能作为案例，不能成为目标工程默认事实。
- 目标工程如果已有研究模板或知识关联 sensor，应把本技能字段映射到既有结构。

## 禁止复制

- 不复制源工程的本地路径、排行、分数、调研对象清单、source revision 或一次性 log。
- 不复制具体技术选型、采购建议、项目阶段、业务场景或 PoC 结果。
- 不把没有运行验证的外部调研结论写成生产接入或验收闭环。

## 目标工程结构自检

目标工程 agent 迁移前先检查：

1. 是否已有 `skills/` 或 agent 技能目录。
2. 是否已有 `articles/`、`concepts/`、`docs/`、`projects/` 或等价知识沉淀层。
3. 是否已有调研模板、技术选型页、源码审计流程或 PoC 报告模板。
4. 是否已有检查脚本能验证入口、回链、模板字段或技能 frontmatter。
5. 如果没有完整知识库结构，先落成一个保守 `SKILL.md`，不要强行铺完整目录。

## 验证要求

- 新技能必须在 README 或等价入口登记。
- 至少用一个技术概念、一个开源工程或一个 AI / 行业方向做干跑自检，确认输出不会越级结论。
- 如果目标工程有 sensor，接入技能成熟度或文档链接检查。
- 最终回复必须写清已更新文件、未迁移的项目事实、检查结果和未验证边界。

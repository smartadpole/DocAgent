# Cross-Project Skill Adoption Prompt

## 定位

本技能把“某个工程已经沉淀好的能力”转换成可交给另一个工程 agent 执行的升级包。

当用户要求修正、升级或重启本 meta-skill 自身时，本技能不再生成迁移提示词，而是进入元技能维护模式：修改本技能、相关 `TRANSFER.md`、sensor、ledger 和 log，运行检查并提交。不能用一段单次提示词替代 meta-skill 升级。

在提示词生成模式下，它生成的是提示词，不是直接执行迁移。提示词必须带：

- 要升级的能力目标。
- 本机已沉淀资料路径。
- 源能力的最小模块清单和覆盖要求。
- 可执行任务书形态：目标 agent 拿到后能按步骤落地，而不是只读到迁移框架。
- 输出模式裁决：通用版、定制版、直接执行、元技能维护四种模式必须先单选，不能混写。
- 哪些可复制、哪些只能抽象吸收、哪些禁止复制。
- 目标工程结构自检与落位要求。
- 指定目标工程时的差异化落位说明。
- 文件、模板、skill、规则、sensor 和入口同步步骤。
- 检查、提交和最终回复要求。

## 适用场景

- 用户说“把某个技能 / 体系迁移到其他工程”。
- 用户要求生成一段提示词，让目标工程 agent 升级某项能力。
- 用户要求把复盘、Issue 分析、验收、代码基线审计、状态推演、服务台账、会议体系、Goal Contract 或 Harness 治理等能力扩散到别的工程。
- 用户指出“提示词里要附上已有知识、方案、模板、本机地址”。
- 用户指出本 meta-skill 导致生成提示词不合理，要求“升级 meta skill / 修改 meta skill / 重启 goal / 修生成机制 / 不要单次生成”。

## 边界

- 本技能默认只生成目标工程执行提示词，不直接修改目标工程。
- 但当用户要求升级 meta-skill 本身时，当前工程就是修改对象；应直接编辑本技能和相关治理文件。
- 不整库复制，不原样搬运项目事实、log 历史、运行 ID、服务实例、业务链路、一次性 handoff 或具体状态。
- 只抽象系统层信息：触发条件、事实源分层、定位方法、输出格式、模板字段、回写守卫、禁止项、验证方式和入口同步。
- 通用提示词场景不预读目标工程；只有用户要求定制提示词或直接执行迁移时，才读取目标工程入口结构。
- 如果用户明确要求“现在去目标工程执行”，再切换到对应工程上下文和执行模式。

## 读取顺序

0. 先判任务模式：通用提示词、定制提示词、直接执行迁移、元技能维护模式四选一。
   - 如果用户说“升级 meta skill”“修改 meta skill”“重启 goal”“处理现有 metaskill 导致的问题”“不是单次生成”，锁定元技能维护模式。
   - 元技能维护模式的交付物是文件修改、sensor / ledger / log 同步、检查和 commit；可以生成候选提示词做验证，但不能把候选提示词当最终交付。
1. 当前用户目标：要迁移哪个能力、目标工程是谁、只是生成提示词、要执行迁移，还是要维护本 meta-skill。
2. `skills/README.md`：确认技能层边界。
3. 源技能：
   - `skills/<skill-name>/SKILL.md`
   - 如果存在，读取 `skills/<skill-name>/TRANSFER.md`
4. 相关资料：
   - skill 中引用的 concept、template、governance、project 入口。
   - `templates/skill-transfer-manifest-template.md`，用于补全迁移字段。
5. 目标工程结构处理按模式分级：
   - **通用提示词**：不读取目标工程；提示词中必须要求目标工程 agent 自行读取本工程入口和结构后再决定落位。用户说“通用版”“不要定制”“只生成可复制提示词”“直接做通用的”时，锁定本模式。
   - **定制提示词**：只有用户明确要求“按某个目标工程定制”“读取目标工程结构”“给某几个工程分别写落位建议”时，才轻量读取目标工程 `README`、`AGENTS`、`docs/`、`projects/`、`skills/`、`templates` 等入口，用来把落位建议写得更准。仅仅点名目标工程不自动等于定制模式。
   - **直接执行迁移**：如果用户明确要求当前 agent 去目标工程落地，必须进入目标工程上下文，先完成结构读取，再改文件。
   - **元技能维护模式**：如果用户要求修复本 meta-skill 的生成机制，优先读取本技能、相关 `TRANSFER.md`、检查脚本、ledger、log；修改后跑 `python3 scripts/check_all.py --only harness-governance` 和完整 `python3 scripts/check_all.py`，并提交。

模式裁决必须遵守最新用户指令。前文出现过目标工程名，但用户后续说“做通用的 / 不要特定工程定制”时，立即切回通用提示词模式，删除具体工程差异化落位、具体路径读取清单和仓库级建议，只保留目标工程自检规则。

如果用户后续说“不是单次生成 / 要升级 meta skill / 修改 metaskill”，立即切到元技能维护模式；停止继续打磨提示词正文，改为修规则、模板、sensor 和日志。

如果源技能没有 `TRANSFER.md`，先根据 `SKILL.md` 和相关页面生成一次性提示词；同时建议补一个 `TRANSFER.md`，不要把完整提示词长期写死。

读取完成后先抽取“源能力覆盖矩阵”，再写提示词。覆盖矩阵至少包括：

- 能力目标：这次迁移到底要让目标工程具备什么能力。
- 方法层：concept、说明页或方法论入口。
- 档案 / 运行层：实例文件放在哪里，索引和命名怎么维护。
- 模板层：可复制骨架、字段和最小章节。
- 技能 / 执行层：触发条件、证据源、工作流、输出格式和禁止项。
- 规则 / 治理层：AGENTS、WORKFLOW、POLICY、ledger、sensor 或目标工程等价入口。
- 行动分流：结果应该回写到哪些 owner 页面，不形成平行看板。
- 验证与提交：目标工程检查、未验证边界和 commit 要求。

生成提示词时必须逐项覆盖矩阵。某一项确实不适用于目标工程时，在提示词中标为“按目标工程结构判断是否需要”，不要静默省略。

覆盖矩阵是生成前的质量门，不是提示词的主叙事。最终提示词优先写成可执行任务书：先给目标工程 agent 一个明确命令、背景目标、参考资料、吸收边界、目标结构自检、需要完成的模块、入口同步、验证提交和最终回复要求。不要让“源能力覆盖清单”这类 meta 说明压过实际执行步骤。

## 输出结构

最终给用户一段可直接复制的提示词，默认包含：

```markdown
请升级目标工程的 <能力名称> 体系。

## 背景和目标

## 参考资料
- <本机路径>

## 吸收边界
- 可以吸收：
- 只能抽象吸收：
- 禁止复制：

## 目标工程结构自检与落位

## 需要建立或更新的模块

## 技能 / 模板 / 规则 / sensor 接入要求

## 行动分流和单一信息源

## 验证和提交要求

## 最终回复要求
```

`源能力覆盖清单` 是生成前自检材料，默认不放进最终提示词正文；只有用户明确要求审计迁移覆盖度时才输出。`目标工程差异化说明` 只在定制提示词或直接执行迁移模式出现，通用提示词禁止出现具体工程小节。

## 迁移包生成规则

### 1. 先识别能力类型

| 类型 | 重点 |
| --- | --- |
| 方法体系 | concept / docs 方法页、档案入口、模板 |
| 执行技能 | skill 触发、证据源、工作流、输出格式、禁止项 |
| 治理能力 | AGENTS / WORKFLOW / POLICY、ledger、sensor、模板 |
| 研发事项体系 | Gate / FP / EP / TASK、risk、issue、AP、report、验收和状态回写 |
| 运行能力 | service registry、部署、健康检查、报告和事故 |

### 2. 列资料路径，不只列提示词

资料路径至少分成：

- 核心 skill。
- 方法论 / concept。
- 模板。
- 规则 / workflow。
- 运行层入口或档案入口。
- 检查脚本或 sensor。

路径必须使用本机绝对路径，便于目标工程 agent 直接读取。

### 3. 先做源能力覆盖，再组织提示词

不要因为追求简洁，把源能力压缩成几个泛化段落。提示词应该先回答“目标工程要补齐哪些能力模块”，再回答“这些模块落到哪里”。

如果 `TRANSFER.md` 已经写了“目标工程应新增或更新”“生成提示词时必须包含”“验证要求”等清单，最终提示词必须逐项承接这些清单；只能改写成目标工程语言，不能只摘摘要。

对于复盘、Issue 分析、验收、代码基线审计、Goal Contract、Harness 治理这类复合能力，提示词默认要保留完整模块拆解。只有用户明确要求短版时，才可以压缩，但仍要保留资料路径、吸收边界、结构自检、核心模块、行动分流、验证和最终回复要求。

### 3.1 任务书优先

生成给目标工程 agent 的最终文本要像一份任务书，而不是一份迁移能力说明。默认使用这种顺序：

1. 直接命令：请升级本工程的 `<能力名称>`，目标不是只新增某个目录或模板。
2. 背景和目标：说明这项能力要解决什么长期问题。
3. 参考资料：列本机绝对路径和必要版本 / 提交锚点。
4. 吸收边界：写清可以吸收、只能抽象吸收、禁止复制。
5. 目标工程结构自检：要求读取目标工程入口并决定落位。
6. 需要建立的模块：按源能力最小模块清单逐项写可执行要求。
7. 入口同步、验证、提交和最终回复：让目标 agent 能照单完成并汇报。

如果 `TRANSFER.md` 或用户提供的对照样稿已经呈现出更强的任务书结构，最终提示词要以那个任务书骨架为主；迁移框架只负责补足资料路径、边界、差异化落位和验证要求。不要为了展示 meta-skill 的结构，把提示词写成“覆盖矩阵 + 迁移说明”的样子。

复合能力迁移默认保留完整编号任务书。不要把“复盘体系的目标 / 参考资料 / 吸收边界 / 目标工程中完成的设计 / 需要建立的模块 / 需要更新的入口 / 最终交付”压缩成短清单。目标工程差异化说明应作为该任务书的补强段落，指出哪些默认落位需要覆盖或避免，而不是替代通用执行主干。

通用提示词的目标不是“泛泛而谈”，而是“目标无关但可执行”。它必须保留完整任务书粒度，但所有落位建议都写成结构自检规则，例如“如果有 `projects/` 则... / 如果没有则... / 如果根目录 `templates/` 是业务模板则...”。不要出现 `prefect`、`customeranalysis` 或任何当前对话里的具体目标工程小节，除非用户重新要求定制。

### 3.2 对照样稿质量门

当用户提供了手写提示词、旧提示词或参考样稿时，输出前必须做一次轻量对照：

- 如果手写样稿的执行顺序更清楚，沿用它的主干。
- 如果 meta-skill 生成稿缺少样稿里的模块、字段、禁止项或最终交付要求，补齐后再输出。
- 如果样稿逐项展开了目标、资料、边界、落位、模块、入口和交付，最终稿也必须保留同等执行粒度；只有用户明确要求短版时才压缩。
- 如果样稿中有项目事实或不可复制信息，只抽象其结构，不复制事实。
- 如果最终稿比样稿更像“说明文”而不是“任务书”，重写为任务书。

### 3.3 Golden Baseline 补丁原则

当用户已经确认某段提示词“更好”或要求“直接做通用版”时，把这段提示词视为 golden baseline。后续改动只能做补丁式增强：

- 保留原有章节顺序和执行粒度。
- 只删除和最新模式冲突的内容，例如具体工程定制段落。
- 只补缺失的资料路径、边界、禁止项、验证或提交要求。
- 不重新摘要、不重排成 meta-skill 模板、不把长任务书压缩成短版。

如果需要从定制版改成通用版，做法是“保留通用任务书主干，移除目标工程小节，保留结构自检条件”，而不是重新生成一份较短的新提示词。

### 3.4 Baseline 对比评分

当用户给出示例并要求生成稿更好时，先把示例拆成 baseline rubric，再生成。复盘体系迁移的 baseline 至少包括：

1. 开头命令：升级完整复盘体系，不只是目录或模板。
2. 目标定义：复盘是长期学习工程，服务未来研发实践、方案设计、工程治理、测试验收、运行质量和 Agent 工作方式。
3. 参考资料：档案入口、模板、通用项目复盘、软件研发复盘、Agent 工作复盘、历史对话 skill、AGENTS、WORKFLOW；如有 `TRANSFER.md`，也必须加入。
4. 吸收边界：不要整库复制，不复制项目事实、log、当前状态、案例原文或一次性治理记录，只吸收系统层信息。
5. 目标工程结构自检：先读目标工程入口，再根据 `projects/`、`docs/`、已有 retrospective / postmortem / incidents / handoff / templates 等结构落位。
6. 模块清单：方法入口、档案入口、模板、软件研发复盘维度、Agent 工作复盘维度、历史对话 skill、行动分流、治理自演进。
7. 入口同步：README、INDEX、AGENTS、WORKFLOW、docs、projects、skills、templates 或等价入口。
8. 最终交付：读取结构、说明推荐落位、更新模块、同步入口、跑检查、提交 commit、最终回复 commit hash。

生成稿只有在满足全部 baseline 并至少新增一类有效增益时，才算更好。有效增益包括：

- 补充 `TRANSFER.md`、当前参考提交或版本锚点。
- 更清楚地区分 handoff、incident、issue、log、memory、trace。
- 增加同名目录防误用规则，例如业务 `templates/` 不承接文档模板。
- 增加检查替代方案、未验证边界和最终回复中的未验证项。
- 增加“通用版不含具体工程小节”的模式防线。

输出前必须给出一句内部裁决：`generated >= baseline`。如果生成稿少于 baseline 任一必备项，先修稿，不要输出。

### 3.5 模式污染防线

识别并避免这些不合理输出：

- 用户要通用版，却输出了 `prefect`、`customeranalysis` 或其他具体工程的小节。
- 用户要可复制提示词，却输出大量 meta-skill 解释、覆盖矩阵或生成原因。
- 用户提供了更好的任务书，却被改写成更短、更抽象的版本。
- 目标工程差异化建议覆盖了复合能力主干，导致方法、档案、模板、skill、行动分流、治理自演进或最终交付变薄。

### 4. 写清吸收边界

每份提示词都要明确：

- `可以复制`：模板骨架、字段、章节、检查口径。
- `抽象吸收`：方法、流程、触发条件、证据分层、输出结构。
- `禁止复制`：项目事实、业务名、历史 log、运行 ID、服务路径、一次性状态和本工程特有 handoff。

### 5. 强制目标工程自检和自适配

不要假设目标工程一定有 `projects/`、`docs/`、`skills/` 或 `templates/`。

提示词必须要求目标 agent：

1. 先读取目标工程入口和结构。
2. 判断已有模块能否复用。
3. 没有对应结构时给出保守落位。
4. 更新目标工程自己的入口页和 agent 规则。
5. 跑目标工程已有检查。

生成通用提示词时，不要替目标工程预判目录；只给默认建议和结构自检要求。生成定制提示词或直接执行迁移时，才读取目标工程入口结构。

### 6. 定制模式必须写目标差异

只有用户明确选择定制模式，并且当前 agent 已经读取目标工程入口结构时，最终提示词才增加目标工程差异化说明。每个目标工程至少写清：

- 已读入口和已有相关结构。
- 应复用的既有目录或规则入口。
- 不应误用的相近目录，例如 handoff、log、issue 或 incident。
- 不应误用的同名或近名目录，例如业务 HTML `templates/`、运行输出目录、临时 handoff 附件目录；如果默认建议和目标工程目录职责冲突，必须写出覆盖后的安全落位。
- 如果没有 projects / skills / templates 体系，最小可行落位是什么。
- 哪些模块本轮必须落地，哪些可以按目标工程结构判断后延后。

如果生成的是通用提示词且没有读取目标工程，则不要编造差异化说明；改为要求目标工程 agent 自行完成这一步。

如果用户最新指令要求通用版，即使之前已经读取过目标工程结构，也不得把这些结构事实写进最终提示词；最多把它们用于确认“通用版不应包含目标工程定制段落”。

### 7. 不把提示词当长期主资产

完整提示词是按需生成物。长期主资产是：

- 源 skill 的 `SKILL.md`。
- 源 skill 的 `TRANSFER.md`。
- 相关 concept / template / governance 页面。
- 本 meta-skill。

## 输出前自检

- 是否明确了目标能力，而不只是文件落位。
- 是否先判定并锁定任务模式：通用提示词、定制提示词、直接执行迁移、元技能维护四选一。
- 如果用户要求升级 meta-skill，本轮是否实际修改了本技能或相关治理文件，而不是只输出一段候选提示词。
- 是否包含本机资料路径。
- 是否先抽出了源能力覆盖矩阵，并逐项反映在提示词中。
- 如果用户给出示例，是否完成 baseline 对比评分，并确认 `generated >= baseline`。
- 最终提示词是否是可执行任务书，目标 agent 是否能按顺序完成读取、落位、创建 / 更新、验证、提交和汇报。
- 如果有手写样稿或参考样稿，是否保留了更强的任务书主干，并补齐而不是替换成 meta 说明。
- 如果用户要求通用版，是否完全移除了具体工程小节、具体工程路径读取清单和仓库级落位建议。
- 是否区分方法论、档案 / 页面、模板、skill、规则和 sensor。
- 是否写清了 action sinks / 单一信息源。
- 是否禁止整库复制和项目事实搬运。
- 是否区分通用提示词、定制提示词和直接执行迁移。
- 定制提示词是否包含每个目标工程的差异化落位说明。
- 最终提示词是否比源 `TRANSFER.md` 少了关键模块；如果少了，是否明确说明为目标工程不适用。
- 是否要求目标工程自读结构、自适配落位、跑检查和提交。

## 禁止项

- 不生成只有“新建目录 / 新建模板”的片面提示词。
- 不生成只有“覆盖矩阵 / 边界 / 落位建议”的说明型提示词；目标工程执行版必须有逐项可执行步骤和最终交付要求。
- 不把复合能力压成过短摘要，导致方法、档案、模板、skill、行动分流、治理自演进或验证要求缺位。
- 不把任务书里真正有用的执行顺序改写成 meta-skill 展示结构。
- 不在通用版里输出具体工程定制段落；目标工程名出现在历史上下文中不等于当前输出要定制。
- 不在用户要求“做通用的”之后继续沿用旧的目标工程差异化说明。
- 不把已确认更好的 golden baseline 重新摘要成更短、更空的版本。
- 不输出低于用户示例 baseline 的提示词；如果少了 baseline 必备项，先修稿。
- 不把“升级 meta skill / 重启 goal / 修生成机制”的请求降级成单次提示词生成。
- 不用候选提示词代替 meta-skill 文件修改、sensor 检查、ledger / log 同步和 commit。
- 不遗漏源 skill 和相关模板 / concept / governance 路径。
- 不读取了目标工程结构却不给目标工程差异化落位建议。
- 不把 AcknowledgeBase 的具体项目事实当成目标工程事实。
- 不让目标工程 agent 跳过目标工程结构读取。
- 不在通用提示词生成阶段强行读取目标工程结构。
- 不要求目标工程照搬 AcknowledgeBase 的目录名；只能给默认建议和适配规则。

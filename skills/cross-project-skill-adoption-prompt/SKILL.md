# Cross-Project Skill Adoption Prompt

## 定位

本技能把“某个工程已经沉淀好的能力”转换成可交给目标工程 agent 执行的通用升级提示词。

它只有一个产物：通用迁移提示词。

它适用于所有已沉淀 skill / 能力主题，不只适用于复盘体系。复盘、Issue 分析、验收、代码基线审计、状态推演、服务台账、会议体系、Goal Contract、Harness 治理等都只是可迁移主题示例；具体模块清单必须来自当前源 skill 和它的 `TRANSFER.md`，不能把某一个主题的字段当成所有技能的默认字段。

本技能的抽象层级是“迁移任务书生成器”，不是“某个主题的迁移规则集合”。高抽象不等于压缩细节：通用规则必须保留资料路径、吸收边界、目标结构自检、主题模块、入口同步、验证、提交和最终回复这些不变量；具体待迁移内容则必须由源 skill / `TRANSFER.md` 提供，不能在本 meta skill 里写死。

所有技能迁移默认采用“先上游归一，再目标迁移”的策略：如果某个下游工程已经把能力演化得比 AcknowledgeBase 源技能更成熟，先把它抽象成系统层增量，反哺到本库的源 skill / `TRANSFER.md` / 模板 / sensor，再从本库源能力生成给目标工程的迁移任务书。不要从下游工程 A 直接复制到目标工程 B，也不要让多个工程各自成为平行源。

通用迁移提示词只生成可复制给目标工程 agent 的任务书；目标工程结构读取、落位判断和实际修改都由目标工程 agent 在收到提示词后完成。提示词必须带：

- 要升级的能力目标。
- 本机已沉淀资料路径。
- 源能力的最小模块清单和覆盖要求。
- 可执行任务书形态：目标 agent 拿到后能按步骤落地，而不是只读到迁移框架。
- 哪些可复制、哪些只能抽象吸收、哪些禁止复制。
- 目标工程结构自检与落位要求。
- 文件、模板、skill、规则、sensor 和入口同步步骤。
- 检查、提交和最终回复要求。

## 适用场景

- 用户说“把某个技能 / 体系迁移到其他工程”。
- 用户要求生成一段提示词，让目标工程 agent 升级某项能力。
- 用户要求把复盘、Issue 分析、验收、代码基线审计、状态推演、服务台账、会议体系、Goal Contract 或 Harness 治理等能力扩散到别的工程。
- 用户指出“提示词里要附上已有知识、方案、模板、本机地址”。

## 边界

- 本技能只生成目标工程可执行的通用提示词，不直接修改目标工程。
- 不整库复制，不原样搬运项目事实、log 历史、运行 ID、服务实例、业务链路、一次性 handoff 或具体状态。
- 只抽象系统层信息：触发条件、事实源分层、定位方法、输出格式、模板字段、回写守卫、禁止项、验证方式和入口同步。
- 不预读目标工程；目标工程结构读取写进通用提示词，由目标工程 agent 执行。
- 不输出具体工程小节、具体工程路径读取清单或仓库级落位建议。

## 读取顺序

1. 当前用户目标：要迁移哪个能力。
2. `skills/README.md`：确认技能层边界。
3. 源能力归一判断：
   - 如果用户指定的是 AcknowledgeBase 内已沉淀的源技能，直接读取源技能。
   - 如果用户指定的是某个下游工程或 LifeOS 等工程里已经变强的技能实现，先按模板反哺原则抽象系统层增量，不复制项目事实、业务链路、运行 ID、本地路径或一次性状态。
   - 如果该增量确实适用于所有技能迁移或当前源能力，先更新 AcknowledgeBase 的源 skill / `TRANSFER.md` / 必要模板或 sensor；完成归一后，再从 AcknowledgeBase 源能力生成迁移任务书。
   - 如果本轮没有授权修改上游源，只在提示词中把该下游实现列为“待人工确认的参考增量”，不得把它伪装成已吸收的源能力。
4. 源技能：
   - `skills/<skill-name>/SKILL.md`
   - 如果存在，读取 `skills/<skill-name>/TRANSFER.md`
5. 相关资料：
   - skill 中引用的 concept、template、governance、project 入口。
   - `templates/skill-transfer-manifest-template.md`，用于补全迁移字段。
6. 目标工程结构一律不预读；只把目标工程结构自检要求写进通用提示词。

如果源技能没有 `TRANSFER.md`，先根据 `SKILL.md` 和相关页面生成一次性提示词；同时建议补一个 `TRANSFER.md`，不要把完整提示词长期写死。

## 生成思考循环

本技能不能只在最后做自检。生成提示词时必须按下面六个检查点推进，每一环都要产出中间判断；中间判断默认不放进最终提示词，但必须影响最终文本。

### 1. 执行合同判定

先回答：

- 用户要的是单次通用迁移提示词，还是要求维护本 meta skill。
- 本次要迁移的能力名称是什么。
- 最终产物是什么：一段可复制提示词，而不是迁移说明、覆盖矩阵、实施方案或目标工程改动。
- 本轮是否有用户提供的强样稿、golden baseline、版本锚点或明确禁止项。

如果用户要的是提示词，最终输出必须直接给任务书；不要输出大量 meta-skill 解释。若用户要维护本技能，才修改本技能、模板、sensor 或样例。

### 2. 源能力抽取

从源 `SKILL.md`、`TRANSFER.md` 和相关资料中抽取：

- 触发场景和能力目标。
- 证据源或事实源。
- 必备模块和每个模块的字段 / 判断项。
- 输出格式和最终交付。
- 禁止项和相近材料边界。
- 验证方式、sensor、检查脚本或人工自检。

抽取时区分“通用迁移不变量”和“当前主题内容”。通用不变量只决定任务书骨架；主题内容必须来自源能力，不得从其他样例借字段。

如果存在下游工程强化版，先做一次源能力 delta 判断：

- 下游新增项是否只是项目事实、业务路由、服务实例、运行路径或一次性 handoff；这类不进入源能力。
- 下游新增项是否是可跨工程复用的触发条件、事实源分层、输出结构、模板字段、回写守卫、导出 / 检查策略或 sensor；这类先反哺源能力。
- 源能力是否已经承接了该增量；如果没有，先更新源 skill / `TRANSFER.md` / 必要模板，再生成目标迁移任务书。
- 如果源能力尚未完成归一，最终提示词必须标注“待吸收增量”，不能让目标工程 agent 误以为这是已确认的上游标准。

### 3. 模块展开

对每个必备模块都先写出最小展开单元：

- 目标。
- 必写字段 / 判断项。
- 落位候选或结构自检规则。
- 反模式 / 禁止项。
- 验证点。

如果某个模块无法写出这些内容，说明源资料不足；最终提示词中必须标注目标 agent 应先补查或按目标工程结构判断，不能用空泛句子补位。

### 4. 任务书成稿

按目标 agent 执行顺序组织最终提示词：

1. 直接命令。
2. 背景和目标。
3. 参考资料。
4. 吸收边界。
5. 目标工程结构自检和落位。
6. 需要建立或更新的模块，且每个模块按字段级粒度展开。
7. 入口同步。
8. 验证和提交要求。
9. 最终回复要求。

不要把覆盖矩阵、设计解释或生成原因放在任务书主叙事里。

### 5. 失败模式审查

输出前逐项问：

- 目标 agent 拿到后是否知道第一步读什么。
- 是否知道每个模块应该写哪些字段，而不是只知道模块名。
- 是否知道哪些相近页面不能替代本能力。
- 是否知道没有对应目录时怎么保守落位。
- 是否知道如何验证和提交。
- 是否出现具体目标工程小节、当前工程业务事实或未确认提交锚点。

任一问题答不出来，先重写，不要输出。

### 6. Golden regression 对照

如果当前迁移主题存在 `examples/` 里的 golden 样例，必须用它做产物级对照。当前已知样例：

- `skills/cross-project-skill-adoption-prompt/examples/retrospective-transfer-taskbook-golden.md`：用于“生成一段提示词，把复盘体系迁移到其他工程”。

对照时不要求逐字复制，但必须达到同等任务书粒度。若生成稿比 golden 样例更短、更抽象、缺少字段级模块、缺少禁止项或缺少最终交付要求，判定为失败并重写。

读取完成后先抽取“源能力覆盖矩阵”，再写提示词。覆盖矩阵至少包括：

- 能力目标：这次迁移到底要让目标工程具备什么能力。
- 上游归一状态：源能力是否已经吸收下游强化版的通用增量，未吸收时如何处理。
- 方法层：concept、说明页或方法论入口。
- 档案 / 运行层：实例文件放在哪里，索引和命名怎么维护。
- 模板层：可复制骨架、字段和最小章节。
- 技能 / 执行层：触发条件、证据源、工作流、输出格式和禁止项。
- 规则 / 治理层：AGENTS、WORKFLOW、POLICY、ledger、sensor 或目标工程等价入口。
- 行动分流：结果应该回写到哪些 owner 页面，不形成平行看板。
- 验证与提交：目标工程检查、未验证边界和 commit 要求。

覆盖矩阵里的每一项都必须先判断“本源能力是否需要”。如果需要，就在最终任务书中展开成该主题自己的执行模块；如果不需要，就写成“按目标工程结构判断是否需要”或“不适用于本能力”。不要因为字段名通用，就把不属于该技能的主题内容塞进去。

生成提示词时必须逐项覆盖矩阵。某一项确实不适用于目标工程时，在提示词中标为“按目标工程结构判断是否需要”，不要静默省略。

覆盖矩阵是生成前的质量门，不是提示词的主叙事。最终提示词优先写成可执行任务书：先给目标工程 agent 一个明确命令、背景目标、参考资料、吸收边界、目标结构自检、需要完成的模块、入口同步、验证提交和最终回复要求。不要让“源能力覆盖清单”这类 meta 说明压过实际执行步骤。

## 输出结构

最终给用户一段可直接复制的提示词，默认包含：

```markdown
请升级目标工程的 <能力名称> 体系。

## 背景和目标

## 参考资料
- <本机路径>

## 吸收边界
- 可以吸收：
- 只能抽象吸收：
- 禁止复制：

## 目标工程结构自检与落位

## 需要建立或更新的模块

## 技能 / 模板 / 规则 / sensor 接入要求

## 行动分流和单一信息源

## 验证和提交要求

## 最终回复要求
- 已更新的落位、检查结果、commit hash、未验证边界和后续建议
```

`源能力覆盖清单` 是生成前自检材料，默认不放进最终提示词正文；只有用户明确要求审计迁移覆盖度时才输出。通用提示词禁止出现具体工程小节。

## 迁移包生成规则

### 1. 先识别能力类型

| 类型 | 重点 |
| --- | --- |
| 方法体系 | concept / docs 方法页、档案入口、模板 |
| 执行技能 | skill 触发、证据源、工作流、输出格式、禁止项 |
| 治理能力 | AGENTS / WORKFLOW / POLICY、ledger、sensor、模板 |
| 研发事项体系 | Gate / FP / EP / TASK、risk、issue、AP、report、验收和状态回写 |
| 运行能力 | service registry、部署、健康检查、报告和事故 |

### 2. 列资料路径，不只列提示词

资料路径至少分成：

- 核心 skill。
- 方法论 / concept。
- 模板。
- 规则 / workflow。
- 运行层入口或档案入口。
- 检查脚本或 sensor。

路径必须使用本机绝对路径，便于目标工程 agent 直接读取。

### 3. 先做源能力覆盖，再组织提示词

不要因为追求简洁，把源能力压缩成几个泛化段落。提示词应该先回答“目标工程要补齐哪些能力模块”，再回答“这些模块落到哪里”。

如果本轮涉及“把工程 A 的成熟技能迁移到工程 B”，先判断工程 A 是否只是目标样本还是已经形成可复用增量。可复用增量必须先回到 AcknowledgeBase 源能力；目标工程 B 的任务书只引用归一后的源资料和必要的待确认参考，不把工程 A 的技能正文、目录、项目事实或本地检查脚本原样传给工程 B。

如果 `TRANSFER.md` 已经写了“目标工程应新增或更新”“生成提示词时必须包含”“验证要求”等清单，最终提示词必须逐项承接这些清单；只能改写成目标工程语言，不能只摘摘要。

对于复合能力，提示词默认要保留完整模块拆解。只有用户明确要求短版时，才可以压缩，但仍要保留资料路径、吸收边界、结构自检、源能力核心模块、行动分流、验证和最终回复要求。

### 3.1 任务书优先

生成给目标工程 agent 的最终文本要像一份任务书，而不是一份迁移能力说明。默认使用这种顺序：

1. 直接命令：请升级本工程的 `<能力名称>`，目标不是只新增某个目录或模板。
2. 背景和目标：说明这项能力要解决什么长期问题。
3. 参考资料：列本机绝对路径和必要版本 / 提交锚点。
4. 吸收边界：写清可以吸收、只能抽象吸收、禁止复制。
5. 目标工程结构自检：要求读取目标工程入口并决定落位。
6. 需要建立的模块：按源能力最小模块清单逐项写可执行要求。
7. 入口同步、验证、提交和最终回复：让目标 agent 能照单完成并汇报。

“逐项写可执行要求”不是只列模块名。每个主题模块默认至少写清：

- 模块目标：目标工程为什么需要这个模块。
- 目标工程应写入的内容 / 字段：页面、模板、skill 或规则里必须出现哪些判断项、字段、证据源或步骤。
- 落位候选和自适配规则：有对应目录时怎么复用，没有时怎么保守落位。
- 反模式 / 禁止项：哪些相近材料不能替代它，哪些常见误判必须避免。
- 验证点：目标 agent 怎样证明这个模块真的建立或更新了。

如果某个源能力的 `TRANSFER.md` 已经给出更具体的模块展开字段，必须采用 `TRANSFER.md` 的字段粒度；上面这组只是最低通用结构。

如果 `TRANSFER.md` 或用户提供的对照样稿已经呈现出更强的任务书结构，最终提示词要以那个任务书骨架为主；迁移框架只负责补足资料路径、边界、差异化落位和验证要求。不要为了展示 meta-skill 的结构，把提示词写成“覆盖矩阵 + 迁移说明”的样子。

复合能力迁移默认保留完整编号任务书。不要把“能力目标 / 参考资料 / 吸收边界 / 目标工程结构自检 / 需要建立的模块 / 需要更新的入口 / 最终交付”压缩成短清单。

通用提示词的目标不是“泛泛而谈”，而是“目标无关但可执行”。它必须保留完整任务书粒度，但所有落位建议都写成结构自检规则，例如“如果有 `projects/` 则... / 如果没有则... / 如果根目录 `templates/` 是业务模板则...”。不要出现 `prefect`、`customeranalysis` 或任何当前对话里的具体目标工程小节。

任务书主干必须只描述迁移不变量；主题模块必须由源能力覆盖矩阵驱动。比如源能力是 Issue 分析，就展开 Issue 分析自己的事实源、根因链、分工、联测和回写要求；源能力是验收，就展开验收分层、AP、报告、证据边界和准出要求；源能力是复盘，才展开复盘方法、档案、模板和行动分流。不能把任何一个例子的模块作为默认。

### 3.2 对照样稿质量门

当用户提供了手写提示词、旧提示词或参考样稿时，输出前必须做一次轻量对照：

- 如果手写样稿的执行顺序更清楚，沿用它的主干。
- 如果 meta-skill 生成稿缺少样稿里的模块、字段、禁止项或最终交付要求，补齐后再输出。
- 如果样稿逐项展开了目标、资料、边界、落位、模块、入口和交付，最终稿也必须保留同等执行粒度；只有用户明确要求短版时才压缩。
- 如果生成稿只列出模块标题，没有写出每个模块的目标、必填字段 / 判断项、禁止项和验证点，判定为低于任务书 baseline。
- 如果样稿中有项目事实或不可复制信息，只抽象其结构，不复制事实。
- 如果最终稿比样稿更像“说明文”而不是“任务书”，重写为任务书。

### 3.3 Golden Baseline 补丁原则

当用户已经确认某段提示词“更好”或要求“直接做通用版”时，把这段提示词视为 golden baseline。后续改动只能做补丁式增强：

- 保留原有章节顺序和执行粒度。
- 只删除不符合通用提示词职责的内容，例如具体工程定制段落。
- 只补缺失的资料路径、边界、禁止项、验证或提交要求。
- 不重新摘要、不重排成 meta-skill 模板、不把长任务书压缩成短版。

如果用户给出的 baseline 带有具体工程定制内容，做法是“保留通用任务书主干，移除目标工程小节，保留结构自检条件”，而不是重新生成一份较短的新提示词。

如果 baseline 末尾重复了开头命令，例如又写一次“升级下本工程的某体系”，最终提示词应删除末尾重复句，或把它移到开头作为第一句；不要让目标 agent 把重复句读成追加命令。

如果 baseline 或用户反馈中出现参考提交、版本号或资料锚点，只有在用户明确说它是当前源资料锚点时才作为已确认锚点写入。若它看起来只是临时记忆或未确认上下文，提示词应写成“如需版本锚点，先在源工程确认当前参考提交”，不要把未验证锚点伪装成事实。

### 3.4 Baseline 对比评分

当用户给出示例并要求生成稿更好时，先把示例拆成 baseline rubric，再生成。baseline rubric 必须先按任意技能主题通用字段抽取，再叠加源 skill / `TRANSFER.md` 的主题专属模块。

任意技能主题的 baseline 至少包括：

1. 开头命令：升级目标工程的 `<能力名称>`，说明目标不是只新增某个目录、模板或说明页。
2. 目标定义：说明这项能力要解决的长期问题，以及它应反哺目标工程的哪些实践、流程、规则、模板、验证或 agent 工作方式。
3. 上游归一状态：说明源能力是否已经吸收其他工程的通用增量；如果还没有，先完成抽象反哺或把增量列为待确认参考。
4. 参考资料：源 `SKILL.md`、`TRANSFER.md`、相关 concept / docs、template、governance / workflow、运行入口、sensor 或检查脚本；如有版本 / 提交锚点，按确认状态写入。
5. 吸收边界：不要整库复制，不复制项目事实、log、当前状态、案例原文、运行 ID 或一次性治理记录，只吸收系统层信息。
6. 目标工程结构自检：先读目标工程入口，再根据既有 docs / projects / skills / templates / issues / incidents / reports / governance / scripts 等结构决定落位。
7. 主题模块清单：按源能力覆盖矩阵和 `TRANSFER.md` 逐项展开该能力自己的方法入口、运行 / 档案入口、模板、skill、规则、行动分流、治理自演进、sensor 或其他特有模块。
8. 入口同步：README、INDEX、AGENTS、WORKFLOW、docs、projects、skills、templates、scripts 或目标工程等价入口。
9. 最终交付：读取结构、说明推荐落位、更新模块、同步入口、跑检查、提交 commit，并在最终回复说明已更新位置、检查、commit hash、未验证边界和后续建议。

主题专属内容只能来自当前源 skill、当前 `TRANSFER.md` 或用户提供的样稿。对照样稿如果比生成稿更完整，先保留它的执行顺序和字段粒度，再做通用化补丁；通用化只移除具体工程事实，不删除主题必备模块。

判断“更好”时，使用两层评分：

1. **通用任务书层**：命令、目标、参考资料、吸收边界、目标结构自检、模块清单、入口同步、验证、提交、最终回复是否齐全。
2. **主题覆盖层**：源 skill / `TRANSFER.md` 中的触发条件、证据源、执行流程、输出格式、禁止项、回写守卫、sensor、单一信息源和最终交付是否逐项进入任务书，并且每个主题模块是否展开到字段 / 判断项级别。

只有两层都不缺，才允许输出 `generated >= baseline`。如果通用层完整但主题覆盖变薄，仍然不合格；如果主题内容很详细但缺少目标结构自检、验证或最终回复，也不合格。

生成稿只有在满足全部 baseline 并至少新增一类有效增益时，才算更好。有效增益包括：

- 补充 `TRANSFER.md`、当前参考提交或版本锚点。
- 更清楚地区分该能力涉及的相近单一信息源，例如 handoff、incident、issue、log、memory、trace、report、service registry 或目标工程等价页面。
- 增加同名目录防误用规则，例如业务 `templates/` 不承接文档模板。
- 增加检查替代方案、未验证边界和最终回复中的未验证项。
- 增加“不含具体工程小节”的通用提示词防线。
- 清理 baseline 里的重复结尾命令，并把未确认的提交 / 版本锚点改成先核对再引用。

输出前必须给出一句内部裁决：`generated >= baseline`。如果生成稿少于 baseline 任一必备项，先修稿，不要输出。

### 3.5 模式污染防线

识别并避免这些不合理输出：

- 输出了 `prefect`、`customeranalysis` 或其他具体工程的小节。
- 用户要可复制提示词，却输出大量 meta-skill 解释、覆盖矩阵或生成原因。
- 用户提供了更好的任务书，却被改写成更短、更抽象的版本。
- 生成稿只列“需要建立或更新的模块”标题，却没有给目标 agent 每个模块应写什么字段、避免什么误判、如何验证。
- 把某一个源主题的模块套到所有技能迁移上，例如迁移 Issue 分析、验收或代码审计时仍要求补复盘档案入口和复盘维度。
- 用“通用”当理由删除源 skill / `TRANSFER.md` 里的主题必备模块。
- 目标工程差异化建议覆盖了复合能力主干，导致源能力核心模块、行动分流、治理自演进或最终交付变薄。

### 4. 写清吸收边界

每份提示词都要明确：

- `可以复制`：模板骨架、字段、章节、检查口径。
- `抽象吸收`：方法、流程、触发条件、证据分层、输出结构。
- `禁止复制`：项目事实、业务名、历史 log、运行 ID、服务路径、一次性状态和本工程特有 handoff。

### 5. 强制目标工程自检和自适配

不要假设目标工程一定有 `projects/`、`docs/`、`skills/` 或 `templates/`。

提示词必须要求目标 agent：

1. 先读取目标工程入口和结构。
2. 判断已有模块能否复用。
3. 没有对应结构时给出保守落位。
4. 更新目标工程自己的入口页和 agent 规则。
5. 跑目标工程已有检查。

不要替目标工程预判目录；只给默认建议和结构自检要求。

### 6. 不把提示词当长期主资产

完整提示词是按需生成物。长期主资产是：

- 源 skill 的 `SKILL.md`。
- 源 skill 的 `TRANSFER.md`。
- 相关 concept / template / governance 页面。
- 本 meta-skill。

## 输出前自检

- 是否明确了目标能力，而不只是文件落位。
- 如果能力来自或经过某个下游工程强化，是否先完成上游归一判断，并且没有从下游工程直接复制到目标工程。
- 是否包含本机资料路径。
- 是否先抽出了源能力覆盖矩阵，并逐项反映在提示词中。
- 如果用户给出示例，是否完成 baseline 对比评分，并确认 `generated >= baseline`。
- baseline 是否先使用任意技能主题通用字段，再叠加当前源 skill / `TRANSFER.md` 的主题专属模块，而不是套用复盘字段。
- 是否用两层质量门同时检查了通用任务书完整性和主题覆盖完整性。
- 最终提示词是否是可执行任务书，目标 agent 是否能按顺序完成读取、落位、创建 / 更新、验证、提交和汇报。
- 每个需要建立或更新的模块是否展开到“目标 / 字段或判断项 / 落位 / 禁止项 / 验证点”，而不是只列模块标题。
- 是否只把具体主题内容从源 skill / `TRANSFER.md` 或用户样稿带入，而不是从本 meta skill 的示例带入。
- 如果有手写样稿或参考样稿，是否保留了更强的任务书主干，并补齐而不是替换成 meta 说明。
- 是否清理了 baseline 末尾重复命令，并正确处理了参考提交 / 版本锚点的确认状态。
- 是否完全移除了具体工程小节、具体工程路径读取清单和仓库级落位建议。
- 是否区分方法论、档案 / 页面、模板、skill、规则和 sensor。
- 是否写清了 action sinks / 单一信息源。
- 是否禁止整库复制和项目事实搬运。
- 最终提示词是否比源 `TRANSFER.md` 少了关键模块；如果少了，是否明确说明为目标工程不适用。
- 是否要求目标工程自读结构、自适配落位、跑检查和提交。

## 禁止项

- 不生成只有“新建目录 / 新建模板”的片面提示词。
- 不生成只有“覆盖矩阵 / 边界 / 落位建议”的说明型提示词；目标工程执行版必须有逐项可执行步骤和最终交付要求。
- 不把复合能力压成过短摘要，导致方法、档案、模板、skill、行动分流、治理自演进或验证要求缺位。
- 不把复盘、Issue、验收、代码审计或任何单一主题的模块清单当成所有技能迁移的默认模块清单。
- 不把任务书里真正有用的执行顺序改写成 meta-skill 展示结构。
- 不输出具体工程定制段落；目标工程名出现在历史上下文中也不能进入通用提示词。
- 不把已确认更好的 golden baseline 重新摘要成更短、更空的版本。
- 不输出低于用户示例 baseline 的提示词；如果少了 baseline 必备项，先修稿。
- 不遗漏源 skill 和相关模板 / concept / governance 路径。
- 不把 AcknowledgeBase 的具体项目事实当成目标工程事实。
- 不把 LifeOS、DocCustomeranalysis 或任何下游工程里更成熟的技能实现直接转移到第三个工程；必须先抽象反哺到 AcknowledgeBase 源能力，再从源能力迁移。
- 不让目标工程 agent 跳过目标工程结构读取。
- 不读取目标工程结构。
- 不要求目标工程照搬 AcknowledgeBase 的目录名；只能给默认建议和适配规则。

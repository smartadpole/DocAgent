# Knowledge Linking Transfer

## 能力目标

让目标工程在新增、调研或大改长期知识时，能判断主落位、入口、上位关系、邻接关系、反向回链和验证方式，避免知识孤岛。

## 可以吸收

- 沉淀模式：快速补链、标准知识沉淀、调研沉淀、机制升级。
- 分层落位：raw / inbox / assets、articles、concepts、governance、skills、templates、log 或目标工程等价层。
- 关系画像：主入口、上位页、邻接页、反向回链、来源、适用边界和检查命令。
- 技能迁移场景的关系画像：`skill-transfer`、Transfer Manifest、源 `SKILL.md`、`TRANSFER.md`、任务书模板、sensor 和最终 owner 页面必须互相可发现；manifest 不能只留在最终回复或 log。
- 单一信息源规则：概念、文章、规则、技能、模板各自承担不同职责。
- 验证方式：入口更新、回链检查、专项 sensor 或人工自检。

## 只能抽象吸收

- 源工程的具体知识图谱、已有文章、概念名和专题分类只能作为参考。
- 目标工程如果没有 Obsidian / wikilink 结构，应映射到它自己的 README、docs index、ADR、runbook 或 docs nav。
- 如果目标工程只有单仓文档，先用最小入口和回链，不强行铺完整知识库结构。

## 禁止复制

- 不复制源工程页面清单、内部链接网络、source matrix、日志历史或项目事实。
- 不把某个项目的一次性调研结论写成目标工程通用规则。
- 不把 `log`、PR 描述、handoff 或聊天记录当成唯一知识入口。

## 目标工程结构自检

迁移前检查：

1. 目标工程的长期知识入口在哪里。
2. 是否区分原始资料、稳定知识、执行规则、技能、模板和历史记录。
3. 是否有 docs nav、README、index、sidebar、wikilink 或等价回链机制。
4. 是否已有链接 / frontmatter / docs 检查脚本。
5. 没有相关结构时，先补最小入口和技能，不批量改造全库。

## 验证要求

- 用一个新增知识页或技能页做迁移后干跑，确认它不只被 `log` 发现。
- 检查入口、上位、邻接、来源和适用边界是否齐全。
- 如果新增 sensor，要做一次负向样例或说明未做负向测试的原因。
- 最终回复写清已落位页面、未迁移的项目事实和检查结果。

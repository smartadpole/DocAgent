# 源码工程深度解读工作流

主入口：[[projects/codebase/README]]

上游：[[projects/requirements]]、[[projects/trace]]、[[projects/design/README]]

下游：[[projects/codebase/page-map]]、[[projects/codebase/schema-map]]、[[projects/codebase/infra]]、[[projects/codebase/conflicts]]、[[projects/codebase/reuse-boundary]]、[[projects/design/topics/README]]

这套工作流用于接手已有源码工程时，避免只读几个显眼文件就误以为已经理解完整。它的目标是让 agent 主动完成工程盘点、深读、交叉验证和终态自审。

## 适用场景

- 用户提供一个本地源码工程，希望理解核心功能、输入输出、实现逻辑、风险和复用边界。
- 用户要把已有系统接入当前整体方案，需要判断哪些能直接复用、哪些必须改造。
- 用户询问某个工程是否已经分析清楚、能否生产化、在整体系统里负责什么。

如果用户面对的是外部开源仓库，还处在“是否值得引入 / 怎么引入 / 直接用还是 Fork”的阶段，优先使用 [[concepts/open-source-project-due-diligence]] 和 [[skills/open-source-project-research/SKILL]]。只有进入正式接入、fork 改造或生产化审计后，才升级到本页的 L0-L3 源码工程深度解读。

## 覆盖等级

### L0：工程盘点

只回答“有什么”。这是任何源码解读的最低起点，不能跳过。

必须产出：仓库路径、远程地址、分支、版本、文件规模、主要目录、入口文件、配置文件、启动命令、主要依赖、文档清单、测试清单和外部资料清单。

终态只能说“完成盘点”，不能说“理解清楚”。

### L1：核心链路理解

回答“主流程怎么跑”。适合首轮定位工程角色。

必须产出：核心需求、输入、输出、主流程、调用链、关键数据对象、状态、主要风险、明显缺口，以及与整体方案的初步关系。

终态可以说“核心链路首轮理解完成”，不能说“全量审计完成”。

### L2：模块级完整映射

回答“各模块怎么协作”。适合正式接入设计前使用。

必须产出：页面 / API / CLI / 任务入口完整映射，schema、存储、消息、任务、缓存、配置和外部依赖映射，测试覆盖点和关键未覆盖点，代码事实与文档口径的冲突清单，以及对整体设计的已解决问题、新增疑问和影响页面。

终态可以说“模块级映射完成”，仍需标注未读文件和低可信区域。

### L3：生产接入审计

回答“能不能投入生产，怎么改”。只有达到这一层，才允许说“已经完成完整源码审计”。

必须产出：端到端链路审计，正常、失败、重试、补偿、取消、重跑、人工修正、删除和回滚路径，并发、队列、幂等、限流、状态恢复、观测、告警、安全、权限、密钥、数据合规、正式写库边界、性能与容量假设、可复用 / 需改造 / 不沿用分级、上线前阻塞项和非阻塞风险。

终态只能在证据矩阵和自审清单支撑下说“达到生产接入审计口径”。

## 执行步骤

1. **目标收敛**：先写清本次审计目标和目标等级。用户说“仔细分析”时默认至少 L2；涉及生产、上线、完整源码审计时默认 L3。
2. **证据盘点**：建立证据矩阵，不先下结论。源码、文档、测试、配置、脚本、模板、前端页面、外部资料和示例数据都要标注 `read`、`skimmed`、`indexed`、`missing` 或 `blocked`。
3. **入口和主链路深读**：按启动入口、对外 API、页面、CLI、定时任务或消费者倒推业务主链路，并覆盖核心服务、领域模型、schema、repository、外部 client 和主流程测试。
4. **数据和状态建模**：拆出输入对象、中间产物、最终结果、状态推进者、幂等字段、版本追溯字段、人工修正字段、正式写库边界和缓存 / 证据 / 导出边界。
5. **异常和生产化审计**：从失败路径反推重试、补偿、取消、重跑、并发、进程重启、部分成功、重复写、外部服务失败、日志、监控和排障入口。
6. **代码事实和文档口径对照**：一致内容进入页面图、schema 图、infra 或复用边界；不一致内容进入 [[projects/codebase/conflicts]]；影响整体设计的问题进入设计专题或会议议题。
7. **上层和全局再评估**：每一批新事实都要反向判断它解决了哪个旧疑问、让哪个原假设失效、带来什么新问题，以及影响需求、架构、数据库、部署、运行质量还是复用边界。
8. **终态自审**：交付前写明目标等级、实际达到等级、证据覆盖矩阵、高可信结论、中可信判断、低可信区域、已关闭问题、新增问题和仍需讨论的问题。

## 自动推进规则

如果目标等级尚未完成，且不存在真正阻塞，不允许把“下一轮深挖顺序”只写给用户后停下。agent 应继续选择下一组最有价值、可独立推进的证据包。

自动推进优先级：

1. 阻塞主链路理解的证据：入口、任务、schema、核心服务、结果写入和测试。
2. 影响整体设计的证据：业务事实、任务状态、幂等、正式写库、复核、删除、权限和部署。
3. 能关闭旧疑问的证据：需求页、设计问题池、冲突清单里的未闭环问题。
4. 能暴露生产风险的证据：失败路径、重试、队列、并发、恢复、容量、模型不可用和人工覆盖。
5. 完整性证据：历史文档、TODO、前端交互、导出物、在线资料和辅助脚本。

只有资料不可访问、需要业务拍板、已达到目标等级，或用户明确要求暂停 / 收尾时，才允许停下等待。

## 默认交付结构

每个源码工程分析完成一个阶段后，至少按 [[templates/source-code-audit-report-template]] 回写 [[projects/codebase/README]] 或对应工程小节。不要在工作流页维护第二份模板正文。

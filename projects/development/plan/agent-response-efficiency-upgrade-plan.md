# Agent 响应效率治理升级计划

主入口：[[projects/development/plan/README]]

上游：[[AGENTS]]、[[WORKFLOW]]、[[POLICY]]、[[BRAIN]]、[[projects/README]]、[[projects/status]]  \
下游：[[projects/development/execution/todo]]、[[skills/README]]、[[log]]

## 背景

本轮对比了当前模板库、重治理主控工程、子工程 下的若干子工程和 子工程 的 agent 规则、技能和工作流，结论是：重治理主控工程 的慢主要不是脚本执行慢，而是主控治理链路在每个问题前都会放大读取、判断、验收和沉淀成本。

关键观察：

- 重治理主控工程 的规则入口接近模板库主控层，但工作项实体更多：约 321 个 Markdown、75 个 TASK、24 个 EP、31 个 FP。
- 重治理主控工程 的 `AGENTS`、`WORKFLOW`、`issue-analysis` 和 `work-item-auto-decomposition` 共同形成重启动链；强约束词密度高，简单问题也容易触发完整主控流程。
- 默认检查脚本不是主要瓶颈：`check_project_docs.py` 约 2.3 秒，`check_work_item_matrix.py --strict` 约 0.14 秒。
- 子工程 虽然仓库更大，但多数规则按目录局部加载；只有命中主控 work item 或外部验收时才进入较重的主控协调规则。
- 子工程、子工程、子工程 的规则触发面更窄，通常不会把简单问题升级成完整治理闭环。

## 问题定义

当前模板库已经很擅长避免漏沉淀、误关闭和证据上推，但还缺少一个明确的“响应模式分层”：

- 简单定位问题和正式验收问题使用相近的前置读取负担。
- 只读分析、主控收口、文档回写、验收闭环、规则反哺之间的模式切换不够显式。
- agent 为了避免违反规则，倾向先读完整治理链，再开始输出，导致用户感受到“几分钟才开始反应”。
- 轻量批处理模式只覆盖大量同类材料，不覆盖“单个简单问题的快速诊断”。

## 升级目标

在不削弱证据边界、主控职责和提交闭环的前提下，增加一层可解释的减载机制，让 agent 能先快后重：

1. **快速诊断**：用户只问位置、原因、差异、初判或排查方向时，先给出最小可信分析，不自动进入完整沉淀、验收和提交链。
2. **范围化收口**：用户要求沉淀、更新文档、收尾、验收、关闭、提交或状态裁决时，再进入对应完整流程。
3. **模式可见**：最终回复或工作记录里写清本轮使用的是快速诊断、计划沉淀、文档回写、验收闭环还是规则升级。
4. **证据不降级**：快速模式只能降低前置读取和写入范围，不能把局部证据升级成 `done`、准出或端到端完成。

## 建议模式

### 1. 快速诊断模式

适用：

- 用户问“为什么慢”“在哪里”“差异是什么”“先分析一下”。
- 当前轮不要求改文档、不要求验收、不要求关闭状态、不要求提交。
- 结论不会直接改变项目状态、规则、自动写入边界或验收结论。

最小动作：

- 读取当前仓库入口规则和最相关的 1 到 3 个事实源。
- 能用命令快速量化的，优先量化。
- 输出 `confirmed / likely / possible / blocked` 分级结论。
- 若发现需要长期沉淀，再提示应升级到计划沉淀或规则升级，不在未授权时扩大写入。

禁止：

- 不把快速诊断写成项目级完成。
- 不关闭 EP / TASK / FP / Gate。
- 不把历史报告、handoff 或局部脚本结果当成本轮验收完成。

### 2. 计划沉淀模式

适用：

- 用户明确说“沉淀下来”“形成升级计划”“作为反思和计划记录”。
- 当前结论有长期价值，但还没有拍板为新硬规则。

最小动作：

- 优先写入 `projects/development/plan/` 或对应项目运行层入口。
- 同步 `projects/development/execution/todo`，让后续可以执行。
- 如影响当前主状态，轻量同步 `projects/status` 或项目主页。
- 补写 [[log]]。

禁止：

- 不直接把计划内容写入 [[POLICY]] 或 [[AGENTS]]，除非用户明确要求升级为规则，或内容已经满足规则层准入。
- 不把未验证的优化方案伪装成已经生效。

### 3. 规则升级模式

适用：

- 用户要求把计划变成规则。
- 同类问题已多轮复现，且旧规则无法承接。
- 需要改变默认读取顺序、自动写入边界、收尾规则或 agent 行为约束。

最小动作：

- 按 [[WORKFLOW#0.2.1 收尾怎么执行]] 和规则改动守卫读取 [[AGENTS]]、[[POLICY]]、[[WORKFLOW]]。
- 先判断是改旧规则、补澄清，还是新增模式。
- 同步入口、log 和必要模板。

禁止：

- 不用“提速”为理由弱化原有验收、证据、主控 / 子工程边界和提交闭环。

## 升级步骤

1. **记录计划**：本页作为首轮沉淀，固定问题定义、证据和目标。
2. **补待办**：在 [[projects/development/execution/todo]] 增加执行项，状态先为 `review`。
3. **规则草案**：下一轮若确认执行，把快速诊断、计划沉淀、规则升级三种模式写成 [[WORKFLOW]] 中的流程段落。
4. **技能减载**：检查 [[skills/issue-analysis/SKILL]] 是否需要增加“快速分析”分支，避免所有 issue 类问题都默认进入完整主控分析。
5. **入口提示**：必要时在 [[README]] 或 [[INDEX]] 的研发方法入口补一句模式分层，避免新 agent 只看到重路径。
6. **回归检查**：确认新模式不会绕过文档沉淀、验收分层、非默认参数验证、主控 / 子工程只读边界和 commit 闭环。

## 验收标准

- 新增模式后，用户提出简单只读问题时，agent 能在前置读取后快速给出初判，并说明是否需要升级模式。
- 用户要求沉淀或收尾时，agent 仍能完整更新主入口、log、状态和 commit。
- 用户要求验收或关闭时，agent 仍区分 `local validation`、`service-side validation` 和 `end-to-end validation`。
- 新规则不会把 重治理主控工程 这类主控仓库降级成普通代码仓库；它只让“问题模式”先分流，再决定是否进入主控重流程。

## 当前结论

本页目前是升级计划，不是已经生效的规则。下一步应先把执行项排入待办，再由用户确认是否把“快速诊断模式”正式写入 [[WORKFLOW]]、[[AGENTS]] 或相关技能。
